# 动态皮肤整改：新聊天命令与交接手册

版本：1.0 ｜ 日期：2026-09-26

用途：让一个不了解旧聊天的新执行者，直接在本项目中接手系统性整改。本文提供可复制的命令；技术规范和验收要求以《动态皮肤系统全面整改与验收手册》为准。

**本文没有创建新聊天，也没有启动整改任务或后台自动化。** 用户在新聊天发送下面的命令后，才由那个聊天执行。

## 1. 怎样使用

1. 在 Codex 中打开现有项目 `C:\pxlngu\projects\noname`，然后创建该项目下的新聊天。
2. 确认新聊天能够访问当前实际工作目录。只从 Git 提交创建的新工作树不一定包含这些尚未提交的手册、代码、忽略的素材和历史证据；执行者必须检查，不能默认为完整现场。
3. 将第2节的完整启动命令复制为新聊天第一条消息。不要只写“接着修皮肤”，新聊天不一定知道旧聊天发生过什么。
4. 后续使用第3—7节的命令继续、检查进度、纠偏或验收，不需要重复描述所有皮肤问题。
5. 更换聊天前，让原执行者更新持久状态文件。新聊天先核对状态文件与实际文件，再继续，不盲信聊天摘要。

三份核心文件：

- 本文：`C:\pxlngu\projects\noname\docs\dynamic-skin-new-chat-handoff.md`
- 整改规范：`C:\pxlngu\projects\noname\docs\dynamic-skin-remediation-manual.md`
- 持久状态：`C:\pxlngu\projects\noname\docs\dynamic-skin-remediation-status.md`

持久状态文件当前已建立，明确记录“完整整改尚未开始”。新执行者不得把手册编写、旧局部修复和旧样例通过，当作本轮G0—G6已完成。

## 2. 新聊天完整启动命令

**复制下面整个文本块发送。无需先补充截图，也无需填写占位符。**

```text
请在现有项目 C:\pxlngu\projects\noname 中，实际执行动态皮肤系统的全面整改，不要停留在重新写计划或逐个皮肤调比例。

先完整阅读并核对以下文件：
1. C:\pxlngu\projects\noname\docs\dynamic-skin-new-chat-handoff.md
2. C:\pxlngu\projects\noname\docs\dynamic-skin-remediation-manual.md
3. C:\pxlngu\projects\noname\docs\dynamic-skin-remediation-status.md
再阅读项目中适用的 AGENTS.md，以及整改规范指定的相关代码和历史诊断记录。历史资料是排查线索，实际代码、源素材和新验收证据才是结论依据。

我的目标是：让当前整套皮肤库在约定的实际使用环境中正确、完整、稳定运行，不再让我逐个发现问题、发送截图。默认基准是4934条皮肤，包括原先标记不可用的54条；你必须重新核对当前清单，记录变化，不能擅自减少范围。

请按整改手册的G0—G6和R01—R14推进：先保护实际现场、盘点全库、建立独立正确参考，再修配置解释、版本兼容、坐标、合成、取景和时间行为，最后完成全量视觉、实际游戏、性能、安装与回退验收。请实际编写所需工具、修改代码、运行检查、查看画面并形成证据；不要以“建议下一步”结束本来可以继续执行的工作。

必须遵守：
- 当前工作区有大量已有修改与未跟踪文件，素材和历史输出部分被Git忽略。不要用git reset --hard、git clean或整体覆盖恢复现场；不要把HEAD当作用户实际运行基线。
- 源素材、存档、武将绑定和已有正常功能必须保全。先保存可恢复的实际基线，使用隔离测试存档和候选输出，避免无保护地改写正式安装。
- 不再新增按皮肤ID、中文名称或某张截图坐标调整构图的生产分支。测试和缺陷记录可以使用ID。
- 不能默认千幻聆音原版有问题，也不能默认现有本地适配器正确。区分界面、导入、配置解释、渲染后端和源素材，依据对照定位责任。
- 当前“原生对照”可能读取处理后的模型，部分运行时审计复用了同一读取器。先审查参考独立性，不能让两边一起出错却判为通过。
- 缩略图、大预览、局内头像和互动都要验收；静帧通过不能替代动画、首帧、循环、切换和生命周期检查。
- 文件缺失、未知字段、未知版本、未验证项和失败项要完整列出。不得隐藏、删除、改成静态、降低画质或更新错误期望图来凑出通过率。
- 全库排查和图像审查由你完成，不把逐个报错的工作交回给我。确实缺少无法恢复的源文件或不可替代的产品决定时，带具体证据提出最小必要问题，同时继续其他不受阻的工作。

本次授权你在当前项目范围内开展必要的本地排查、工具建设、代码修复、候选索引生成和测试。日常可逆工作不必反复请求确认；不要擅自清除正式存档、覆盖原始素材、发布到远程或扩大到无关项目。

每个阶段更新 C:\pxlngu\projects\noname\docs\dynamic-skin-remediation-status.md，记录真实完成项、证据路径、未解决问题、运行中的进程/测试、下一步和恢复方式。它是交接记录，不是用来替代真实验证的勾选表。任务需要跨聊天时，先留下可执行的续接信息，不要丢失未完成目标。

最终只有在冻结范围内验收100%通过、已知缺陷为零、待验证项为零、安装物一致且回退演练通过时，才能宣布本轮整改完成。做不到就准确列出剩余项和原因，继续处理可执行工作，不用局部样例通过宣称“完美运行”。

现在开始执行。首次先核对当前现场与状态文件，从尚未完成的最早阶段开始；不要另写一份同内容的整改方案代替行动。
```

## 3. 中断后或跨聊天继续的命令

执行者有新的实际状态记录后，使用这一段。初次启动仍使用第2节。

```text
请继续执行 C:\pxlngu\projects\noname 的动态皮肤系统全面整改。

先读取 docs/dynamic-skin-remediation-status.md 和 docs/dynamic-skin-remediation-manual.md，核对其对应的代码、源哈希、证据文件、运行进程和最后一次测试结果。不要假定旧聊天上下文已经继承，也不要默认状态文件仍然准确。

保留既有基线、用户修改和未完成任务。先判断上次命令是否仍在运行或部分完成，避免重复导入、重复生成同一索引、并发覆盖报告。已完成且输入未变化的有效检查可以复用；输入变化后按影响范围重验。

从最早未通过的阶段继续实际实施，持续更新持久状态。不要重做已经证实完成的工作，也不要只回复一份计划。未解决的原目标、最新文鸯反馈和全库验收要求继续有效。
```

如果状态文件缺失：让执行者先从代码、输出和历史证据重建可信状态，缺证据部分标记待核验，不凭记忆补写“通过”。

## 4. 要求真实进度的命令

```text
请核对动态皮肤整改的实际进度，并简洁报告：
1. 当前所在阶段和已完成任务，对应证据在哪里；
2. 冻结皮肤总数，以及通过、失败、阻塞、待验证各多少，分母是否闭合；
3. 正确参考覆盖了哪些类别，视觉审查完成多少；
4. 本轮改动影响哪些条目，原正常效果是否有回归；
5. 剩余根因、真正需要我提供的信息，以及你接下来能直接执行的工作。

不要把代码写完、命令退出码为0、目录标记可用或历史样例通过当作全量验收完成。更新状态文件后，继续不受阻的整改工作。
```

不能要求执行者在没有记录时估算一个好看的百分比。没有对应证据的条目应算待验证。

## 5. 发现又在逐皮肤补丁时的纠偏命令

```text
请停止继续扩大基于单个皮肤截图的构图猜测，回到全面整改手册。

请检查最近的改动是否依赖皮肤ID、名称、固定人物坐标或没有独立参考的比例阈值。列出这些规则的证据、影响范围和对正常皮肤的风险；对缺乏依据的候选改动，按已保存基线仅回退本轮相关文件或规则，不要撤销其他工作。

随后从源配置语义、实际骨骼版本、图层坐标、遮罩和独立参考定位同类根因。建立该类全部条目的对照，再修改公共逻辑。不要让我继续补发该类别每个皮肤的截图。
```

这是对方法的纠正，不是让执行者盲目删除所有旧代码。回退必须知道本轮起点与改动归属。

## 6. 更换聊天前保存交接的命令

```text
我要把动态皮肤整改转交到另一个聊天。请先保存现场并更新：
C:\pxlngu\projects\noname\docs\dynamic-skin-remediation-status.md

写清当前阶段、已修改文件、有效基线、证据目录、已通过检查及其输入版本、失败项、尚未验证项、候选与正式安装的差别、仍在运行的进程或测试，以及下一步可以直接执行的操作。

对正在运行的任务，明确其命令、工作目录、进程标识、输出路径和当前状态；不要宣称工具会话ID一定能在新聊天复用。不能安全留后台的任务应妥善停止，并保留已完成结果。

不要清理源素材、正式存档、未提交代码或排查证据。不要为了交接重新建立覆盖原基线。完成后告诉我状态文件路径，再结束本轮工作；不要把未完成目标标成完成。
```

交接本身不要求创建新聊天、定时任务或远程推送。新聊天由用户选择何时创建。

```text
请按动态皮肤全面整改手册第19节执行最终交付核验，不要只汇总先前成功的测试。

从冻结清单反推所有应验收单元，检查是否漏条目、漏动作、漏入口、漏设备或漏视觉审查。核对正确参考独立性、原54条不可用项、历史及最新用户反馈、安装副本、供应库、索引、缓存、实际游戏表现、性能和回退演练。

不允许通过删失败项、修改分母或跳过未知类别来通过验收。区分实机与软件渲染、源资源问题与代码问题、未变化与已正确。

如任何项失败或待验证，更新缺陷和状态记录，继续修复可执行部分。全部达标后，输出带证据路径的最终报告，明确交付版本、素材范围、目标环境及全部统计。
```

## 8. 新执行者第一轮应该做到什么

第一轮至少应产生以下可检查结果；全库扫描过大时允许分片，但必须说明当前已扫描范围和续跑位置。

- 找到并读完核心手册，确认当前工作目录与素材位置。
- 查看实际 Git 状态、已有运行进程和证据文件，识别尚未提交/被忽略的工作。
- 建立或核对可恢复的当前现场，而非把 Git HEAD 当作基线。
- 重算目录总数和不可用项；明确哪些数字只是历史快照。
- 登记最新反馈和已有缺陷，开始盘点配置消费、实际版本及参考工具的独立性。
- 在状态文件记录本轮已执行的工作、证据和下一步，而不是只复制整改手册的目录。

若新执行者第一轮直接针对某个武将调比例，或者重新写一份计划后询问“是否开始”，应使用第5节纠偏命令。

## 9. 状态文件维护规则

固定入口为 `docs/dynamic-skin-remediation-status.md`。新执行者每次跨阶段、重要测试结束或准备交接时更新。

必须保留：

1. 最后核对日期、代码快照/工作区身份和当前阶段。
2. 冻结分母与当前目录分母，两者的差异解释。
3. G0—G6和R01—R14的真实状态，不根据聊天语气推断完成。
4. 已修改文件和正式安装/候选输出的对应关系。
5. 基线、原始参考、正确参考、旧回归基线各自的位置和用途。
6. 测试命令、环境、输入版本、退出状态和完整报告路径。
7. 开放缺陷、未知类别、资源缺失和不可替代的用户问题。
8. 运行任务及恢复办法；下一步无需重新推理即可执行。

绝对路径适用于当前机器；迁移机器时先核对新的项目根目录并更新路径。不要把已经失效的临时文件路径作为唯一证据。状态文件只能记录真实事实，不虚构已执行命令或已查看画面。

## 10. 常见交接错误

| 错误 | 应采用的方法 |
| --- | --- |
| 只发送“继续修复” | 发送第2节或第3节，并指明同一项目 |
| 假定新聊天能看到所有旧聊天 | 使用持久手册、状态及证据，不依赖隐含历史 |
| 新工作树没有本地素材却开始改 | 先核对文件可见性和实际现场，明确缺失原因 |
| 历史41项测试通过就从G5开始 | 将其作为历史局部证据，按当前状态核对阶段 |
| 目录写着可用就计入视觉通过 | 检查完整验收记录和实际画面 |
| 从当前错误代码重新生成“正确参考” | 使用独立且可追溯的原始参考 |
| 新聊天又要求用户报剩余所有皮肤 | 由执行者扫描目录、查看画面、归类根因 |
| 手册写了目标就宣称必然零故障 | 按已约定范围和实际证据验收，真实列明阻塞 |
| 交接前清理所有未跟踪文件 | 保留现场，仅清理本轮明确拥有且不再需要的临时产物 |

**最简使用方式：在同一项目的新聊天中，发送第2节完整命令。后续只需按需要使用继续、进度、纠偏和验收命令。**
