## 8. 新执行者第一轮应该做到什么

第一轮至少应产生以下可检查结果；全库扫描过大时允许分片，但必须说明当前已扫描范围和续跑位置。

- 找到并读完核心手册，确认当前工作目录与素材位置。
- 查看实际 Git 状态、已有运行进程和证据文件，识别尚未提交/被忽略的工作。
- 建立或核对可恢复的当前现场，而非把 Git HEAD 当作基线。
- 重算目录总数和不可用项；明确哪些数字只是历史快照。
- 登记最新反馈和已有缺陷，开始盘点配置消费、实际版本及参考工具的独立性。
- 在状态文件记录本轮已执行的工作、证据和下一步，而不是只复制整改手册的目录。

若新执行者第一轮直接针对某个武将调比例，或者重新写一份计划后询问“是否开始”，应使用第5节纠偏命令。

## 9. 状态文件维护规则

固定入口为 `docs/dynamic-skin-remediation-status.md`。新执行者每次跨阶段、重要测试结束或准备交接时更新。

必须保留：

1. 最后核对日期、代码快照/工作区身份和当前阶段。
2. 冻结分母与当前目录分母，两者的差异解释。
3. G0—G6和R01—R14的真实状态，不根据聊天语气推断完成。
4. 已修改文件和正式安装/候选输出的对应关系。
5. 基线、原始参考、正确参考、旧回归基线各自的位置和用途。
6. 测试命令、环境、输入版本、退出状态和完整报告路径。
7. 开放缺陷、未知类别、资源缺失和不可替代的用户问题。
8. 运行任务及恢复办法；下一步无需重新推理即可执行。

绝对路径适用于当前机器；迁移机器时先核对新的项目根目录并更新路径。不要把已经失效的临时文件路径作为唯一证据。状态文件只能记录真实事实，不虚构已执行命令或已查看画面。

## 10. 常见交接错误

| 错误 | 应采用的方法 |
| --- | --- |
| 只发送“继续修复” | 发送第2节或第3节，并指明同一项目 |
| 假定新聊天能看到所有旧聊天 | 使用持久手册、状态及证据，不依赖隐含历史 |
| 新工作树没有本地素材却开始改 | 先核对文件可见性和实际现场，明确缺失原因 |
| 历史41项测试通过就从G5开始 | 将其作为历史局部证据，按当前状态核对阶段 |
| 目录写着可用就计入视觉通过 | 检查完整验收记录和实际画面 |
| 从当前错误代码重新生成“正确参考” | 使用独立且可追溯的原始参考 |
| 新聊天又要求用户报剩余所有皮肤 | 由执行者扫描目录、查看画面、归类根因 |
| 手册写了目标就宣称必然零故障 | 按已约定范围和实际证据验收，真实列明阻塞 |
| 交接前清理所有未跟踪文件 | 保留现场，仅清理本轮明确拥有且不再需要的临时产物 |

**最简使用方式：在同一项目的新聊天中，发送第2节完整命令。后续只需按需要使用继续、进度、纠偏和验收命令。**
