状态：待执行的开发基线。日期：2026-09-11。

本方案取代“继续完善 IP 输入页”的产品方向。此前 `connection-and-exit.md` 记录的是局部修复，不代表已完成本方案。当前工作区已有未提交修改，后续开发应接续并审阅这些修改，不得直接覆盖或回退。

本文只分析游戏本体及服务器代码，忽略扩展包和安装的扩展内容。本轮仅编写文档，不修改程序、不构建、不运行测试。后续延续“开发由助手完成、测试由用户执行”的约定；文中的验收项目是给用户的执行清单。没有实际公网验收记录时，只能标记“开发完成、待验证”，不能声称公网可玩已验证。

## 1. 目标与三轮交付原则

目标是一个能部署在用户自有服务器上的公网休闲对战版本：玩家选择单机或联机后，点击同一组玩法卡片，分别进入本地游戏或该玩法的在线大厅；支持房间浏览、搜索、创建、加入、好友邀请、快速匹配、准备开局、真实对局、断线重连和结算返回。

“行业标准”在这里落实为明确的产品流程、服务端状态管理和异常处理，不作为某一认证或无限功能集合。会话加入、好友关系、匹配队列及服务器运行对局分别承担不同职责，不能用一个连接按钮代替。相关设计参考 [Unity 会话加入与重连](https://docs.unity.com/en-us/mps-sdk/join-session) 和 [Nakama 匹配说明](https://heroiclabs.com/docs/nakama/concepts/multiplayer/matchmaker/)，不引入这两个产品的付费服务依赖。

最多安排三轮开发里程碑，每轮都覆盖前端、接口、后端、部署资料和缺陷修复，不能拆成“第一轮画 UI、第二轮假数据、第三轮才接游戏”。一轮是完整交付阶段，不等于一次短对话，也不承诺固定工时。

| 轮次 | 交付主题 | 用户应能完成的操作 |
| --- | --- | --- |
| 第一轮 | 新入口、真实账号/会话、房间大厅、服务器托管对局闭环 | 选择联机→身份→创建/搜索/加入房间→准备→完整对局→结算 |
| 第二轮 | 好友对战、匹配、自动重连及玩法适配 | 添加好友并邀入房；进入真实队列匹配；断线后恢复原席位继续游戏 |
| 第三轮 | 公网部署、版本与安全收口、UI 全状态精修、用户验收闭环 | 使用域名跨网络完整游玩，依据日志定位并修复公网验证问题 |

三轮内必须完成上述核心功能。排位赛、商城、语音、公会、赛事、跨区域调度、所有自定义规则及全部模式服务端化不属于首版。本方案默认身份标准玩法、斗地主标准玩法为完整上线范围；其余本体玩法保留卡片，依据能力表开放，不能伪装为已经支持。此范围是控制三轮规模的方案建议，不是用户已同意缩减所有玩法。

## 3. 产品入口与页面流程

### 3.1 单机/联机是会话类型，身份等是玩法

新增独立字段 `sessionType: offline | online`，玩法使用 `modeId`，不能继续把 connect 当作用户可选玩法。旧引擎内部暂时使用 connect 桥接时，必须由适配器封装。

```text
启动首页：无名杀                         [单机 | 联机]  好友/个人资料  退出
                    身份  国战  斗地主  对决  单挑 ...

单机 + 身份 → 原身份设置/开局 → 原单机逻辑
联机 + 身份 → 身份大厅 → 房间列表 / 创建房间 / 快速匹配 / 好友邀请
                              ↓
                       等待房间 → 准备 → 真实对局 → 结算
                              ↑                       ↓
                              └──────── 再来一局 / 返回身份大厅
```

首次进入默认单机，此后记住用户主动选择。切到联机时建立平台会话并显示服务连接状态，不弹原生 confirm、不自动读取剪贴板，不在网络失败时悄悄切成单机。

点击联机玩法卡片必须先展示对应大厅，不能直接排队。大厅显示玩法标题和子玩法过滤；不支持的玩法显示“此玩法暂未开放联机”及原因，保留原画和单机入口。房间中切模式、切单机或退出要明确处理离房；排队时先取消队列再切换，不能留下幽灵排队记录。

旧保存配置 `mode=connect` 迁移到 `sessionType=online`，选择上次在线玩法或身份。旧 `last_ip` / `recentIP` 不覆盖正式服务器配置；旧 reconnect_info 不能绕过新账号认证。

### 3.2 统一在线页面

| 页面 | 必备内容与行为 |
| --- | --- |
| 在线首页/玩法大厅 | 头像昵称、连接状态/实测延迟、玩法导航、房间搜索、规则筛选、真实房间卡片、创建与匹配主按钮、好友抽屉 |
| 创建房间 | 房名、玩法/子玩法、人数、规则预设、公开/好友/邀请可见性、可选房间密码、旁观设置；服务端验证合法组合 |
| 等待房间 | 房间码、席位、准备状态、房主标识、邀请、房间聊天、规则摘要；开局条件、踢人和离房权限明确 |
| 匹配中 | 当前玩法/人数规则、已等待时间、取消操作；有可靠统计才显示预计等待，不伪造在线人数或匹配进度 |
| 好友面板 | 按用户码搜索、申请/同意/拒绝、删除/屏蔽、在线/房间中/对局中、邀请与邀请处理 |
| 对局恢复层 | 正在重连、尝试次数、座位保留剩余时间、手动重试、返回大厅；恢复前锁定对局操作 |
| 结算 | 真实结果、再来一局、返回同玩法大厅；游戏实例结束不等于立即删除社交房间 |
| 服务不可用 | 明确说明连接失败/维护/版本不兼容，并提供重试和单机入口，不能展示空列表冒充服务正常 |

邀请使用短时邀请码或可分享深链接，主动点“粘贴邀请”才申请剪贴板权限。登录前接收邀请只保存待处理意图；登录后再校验可见性、容量、版本与过期状态。链接本身不包含账号令牌。

### 3.3 视觉要求

保留现有武将原画、三国风背景与金棕配色；统一深色面板、柔和遮罩、边框、圆角、按钮层级和字阶。首页仍是精美玩法卡片，大厅是有信息层级的房间卡片/列表，不能改成后台管理表格或白底表单。

新增一套在线 UI 设计变量：背景/面板/描边/强调/危险/成功色，字号层级，8px 间距基准，按钮高度 44px 起，键盘焦点。大屏采用玩法导航、房间区、好友区；窄屏好友变抽屉、筛选折叠、主按钮保持可达。参考适配宽度为 360、768、1280、1920px，最终由用户截图验收。

所有页面同时设计 loading、empty、error、offline、disabled、pending 和正常状态。只对未进入状态使用骨架；请求失败不能显示“暂无房间”。在线壳层隐藏暂停、托管、整理手牌等对局专用工具，对局开始后再显示；右侧保留明确退出入口。

## 4. 技术方案与最高风险

### 4.1 采用单服起步的模块化架构

建议复用项目 TypeScript、Vue 和 ws；平台 HTTP API 使用 Fastify，PostgreSQL 保存持久数据。初版单平台进程管理实时状态，不默认引入 Redis、Kubernetes 或微服务集群；后续真有多实例需求再扩展。

```text
浏览器 / Electron / Android
            │ HTTPS + WSS（统一域名、正式入口）
       TLS 反向代理 + 静态客户端
            │
       平台服务 packages/server
       认证 / 好友 / 房间 / 匹配 / 会话恢复 / 版本能力 / 管理
            ├── PostgreSQL：账号、关系、房间元数据、结果、迁移记录
            └── 内部对局调度器 → 游戏执行 worker → 本体现有游戏引擎
```

`packages/fs` 是当前本地文件服务，不得作为公网平台接口暴露。生产环境不能开放其任意读写文件路由，也不能直接把整个仓库目录作为静态根目录。

### 4.2 玩家房主与游戏执行者分离

用户创建房间后拥有“房间管理权”，不意味着其浏览器负责维持所有玩家的游戏。一局游戏由用户服务器上的独立 worker 托管，房主关闭页面后服务器继续推进，其他玩家不中断；等待阶段可转移房间管理权。无需把全部内存游戏状态迁移给另一位玩家。

仅转发消息的服务器不能提供权威规则裁决，这是中继与权威执行的实质差别，参考 [Nakama 对中继限制的说明](https://heroiclabs.com/docs/nakama/concepts/multiplayer/relayed/)。本项目要复用既有引擎，需要额外的引擎适配工作，不能把 ws 服务加几个接口视为已完成。

**第一轮的首要技术任务：托管执行适配。** 现有引擎深度依赖 DOM，方案选用受限的服务端 headless Chromium worker 运行固定版本本体，平台通过内部通道驱动它；这是一种兼容性执行容器，不是重写纯 Node 游戏引擎。Playwright 仅作为进程控制库，不模拟生产环境的人类点按钮，不用于在用户未授权时执行测试。[官方 Docker 资料](https://playwright.dev/docs/docker) 可供构建环境参考，具体镜像版本在实施时锁定。

worker 适配必须处理：

1. 无交互启动：绕过新手引导、平台询问与本地弹窗，按服务器固定资源清单加载本体。
2. 完整玩家席位：没有假房主占用一席，也不能默认机器人冒充真实玩家。分离 game.me 的执行环境假设与真人席位，适配初始化、选将、回合推进和结算。
3. 内部连接身份：worker 只接受平台签发的实例授权，玩家不能注册成执行 worker；外部输入不得通过 exec/函数反序列化取得执行能力。
4. 状态投影：服务端掌握完整牌局，玩家仅收到自己可见的手牌、身份与合法交互；旁观默认无隐藏信息。
5. 单局隔离和清理：一局一个可回收执行单元，限制资源、时长、网络出口和文件权限；不加载扩展，不接受客户端上传代码。
6. 运行生命周期：分配、就绪、开局、结束、超时、崩溃均回报平台，准备阶段失败必须回滚房间/匹配占位。

这是最高风险项，应先于大量好友/大厅页面开发。第一轮先交付身份标准规则的完整执行适配，再扩房间 UI。若旧引擎在无真人房主席位下无法推进，必须在第一轮内解决或明确报告此项未完成；不能默默改为玩家浏览器托管后宣称达到原方案，也不能把它藏成第四轮。

服务端托管不等于已经完成全部反作弊。必须限制客户端请求为当前合法选择、校验席位与回合、限制参数和事件引用；遗留函数广播只能由可信 worker 单向生成，平台业务协议一律只用结构化数据。

### 4.3 首版边界

服务器 worker 存活时，玩家断网、刷新及房主离开应能恢复/继续。worker 本身崩溃或整机断电后的任意时刻无损续局，需要可序列化执行栈或确定性重放，本体目前没有已证明可用的此类能力。首版要求异常终止、不重复结算、释放占位和明确提示，不承诺崩溃后无损续局。

因此数据库房间记录、客户端可见快照、运行中的引擎执行状态是三种东西；不能把保存一个 arenaState 称为完整灾备恢复。账号、好友和已完成结果必须可从数据库恢复。

## 5. 数据、接口与状态约定

### 5.1 身份与权限

第一轮交付稳定用户 ID、公开用户码、昵称头像、注册/登录/登出和刷新会话。建议首版采用用户名+密码，使用成熟密码哈希实现，限频并防止账号枚举；昵称不能当唯一身份。可选游客会话仅用于浏览，好友和正式匹配要求稳定账号。密码找回采用一次性恢复码方案；邮件找回不作为依赖，避免服务器尚无邮件服务时阻塞上线。

访问令牌短时有效；刷新凭据可轮换和撤销。浏览器优先同源 HttpOnly/Secure Cookie，写接口校验来源/CSRF；原生端凭据使用平台安全存储。WSS 通过已认证会话或一次性连接票据接入，不把长效令牌放进 URL 或日志。公开用户码、roomCode、accountId、sessionId、gameInstanceId 各自独立，禁止复用现有 onlineKey 作为通用鉴权密码。

### 5.2 最小实体

| 实体 | 关键字段/约束 |
| --- | --- |
| Account / Session | accountId、publicCode、credentialHash、refreshSession、expiresAt、revokedAt；凭据不可明文存储 |
| Friendship / Block | 双方 ID、requested/accepted/rejected；唯一关系约束、屏蔽优先 |
| Room | roomId、roomCode、ownerId、modeId、rulesPreset、visibility、passwordHash、status、revision、gameInstanceId |
| RoomMember | accountId、seat、ready、presence、disconnectDeadline；唯一席位，账号只能占一个活动游戏席位 |
| Invitation | inviteId、roomId、sender、recipient、expiry、consumedAt；接受时重新查权限和容量 |
| MatchTicket / Party | ticketId、members、modeId、rulesHash、region、state、createdAt、reservationDeadline |
| GameInstance / Result | instanceId、buildHash、workerLease、state、resultId；结果只能由内部 worker 上报且幂等保存 |

房间列表只返回公开信息。好友房仅授权好友可见，邀请房不进入搜索结果；密码房搜索结果不带密码。查邀请码不是万能绕权入口。

### 5.3 建议接口契约（第一轮冻结）

HTTP `/api/v1`：认证与会话、`me`、服务器能力/构建版本、玩法能力表、分页房间查询、好友查询/申请、账号资料及最近对局结果。房间查询支持 modeId、rules、状态、人数、roomCode 精确查找和房名关键词；分页排序必须稳定，错误与空结果分开。

WSS `/ws/v1`：room.create/join/leave/update/ready/start、friend.invite、invite.accept/decline、match.enqueue/cancel/accept、session.resume、game.action，以及对应服务端事件。认证、数据库与 WS 共同使用同一权限模块。

统一消息 envelope：`protocolVersion, type, requestId, payload`；响应包含 `requestId, ok, code, message, revision`；推送包含 `eventId, streamId, sequence`。requestId 用于幂等，revision 防止过期页面覆盖新房间设置。错误码至少包含 AUTH_EXPIRED、VERSION_MISMATCH、ROOM_FULL、ROOM_CLOSED、FORBIDDEN、ALREADY_IN_GAME、QUEUE_CONFLICT、RESUME_EXPIRED、SERVICE_BUSY。

房间修改和抢席由服务器串行处理/数据库约束保障，匹配预留也经过同一套入房服务。请求自报的 ownerId、seat、胜负均不能直接采信。房间设置变更会取消原准备状态；对局启动后冻结规则。

### 5.4 状态机

```text
连接：offline → connecting → authenticating → lobby
                           ↘ reconnecting → resuming → 原活动状态
                           ↘ expired / unavailable
房间：waiting → starting → in_game → finished → waiting
                  ↘ waiting（分配失败）      ↘ closed
匹配：queued → reserved → confirming → allocating → assigned
         ↘ cancelled / expired    ↘ 回队列或取消（按失败参与者分别处理）
席位：online → disconnected（保留）→ resumed / abandoned
```

每次转换必须定义权限、超时、失败回滚及通知事件。刷新不能重复建房、重复排队或重复启动 worker。

## 6. 三轮实施清单

执行顺序：

第一轮用户验收：

- 单机身份仍正常进入本地逻辑；两套主题均无联机玩法卡片。
- 两个不同账号在真实接口下创建、搜索和加入同一房间；满房/锁房/无权限状态正确。
- 身份标准规则可由真实玩家准备、选将、推进到实际结算，无人工操作服务器页面，无假玩家占位。
- 房主用户关闭浏览器后，其他玩家对局继续，证明执行者在服务器。
- 结算或离房返回同玩法大厅；服务器无法访问时显示错误，不出现假空房间。

交付记录：准确列出支持的身份人数/规则、本体包清单、已知问题、用户验收结果。规则可配置不等于所有组合都已支持；未验收保持待验证。

### 第二轮：好友、真实匹配、自动恢复与第二玩法

当前开发交接：见 [第二阶段交接与开发说明](online/phase-2-handoff.md)。本轮仍由用户负责运行验证；源码已按第二阶段范围继续开发，未运行测试或公网验收。

1. 完成好友关系持久化、用户码搜索、申请处理、在线状态、删除/屏蔽；实现带有效期和目标人的房间邀请。邀请无空位时返回原页面，不把当前房间踢掉再报错。
2. 实现真实匹配服务，与房间、worker 分配共用流程。按玩法、规则预设、人数和区域分队列；先入先出，首版无段位匹配。人数不足继续等待，不伪造成功。
3. 首版支持单人快速匹配和好友私房对战。额外支持小队共同排队时：队长发起、全员同意并准备、整队原子预留；组队只进兼容组队规则池，身份隐藏阵营默认禁止预组队匹配，避免串通。不能把好友私房当成已经支持组队匹配。
4. 取消与匹配成功竞态由服务器裁决：取消先提交则不分配，分配先提交则返回真实状态；15 秒确认窗、超时释放席位，接受者可按原等待时间回队列，拒绝者退出。worker 无容量返回 SERVICE_BUSY，不生成不可开的房间。
5. 自动重连：指数退避与抖动，建议 1/2/4/8 秒、上限 10 秒，座位默认保留 120 秒，配置可调；识别主动退出、网络失败、鉴权失败、版本失败，后两者不无限重试。
6. 账号重新认证后校验 session/instance/seat/generation，注销旧连接；进行中的对局以 worker 状态为准。客户端刷新后也能查询 active-session 恢复，不依赖单个 localStorage 玩家 ID。
7. 恢复采用“当前可见状态快照 + 当前可操作提示”重建客户端，不能只补昵称/头像。历史动画不重播；过期选择不重发。对局动作有 actionId、turnId、expectedRevision，去重防止断线后重复出牌。
8. 网络断开期间沿用并明确展示托管策略；超时后服务器标记放弃，机器人仅作可识别托管，禁止伪装成匹配玩家。恢复成功取消其后续自动决策，但已执行动作不能撤销。
9. 接入斗地主标准规则，并完成其房间、匹配、结算和恢复。其余本体模式逐项记录能力，不把前端卡片可见误当成已服务端化。

第二轮用户验收：好友重登后仍存在；陌生人不能接受定向邀请；三个真实账号能匹配斗地主并完成对局；多人身份在合法规则下可匹配；取消后不会突然入房；拔网恢复和页面刷新后席位、手牌、身份、回合一致；原房主断开不终止其余玩家；不允许两个连接同时控制同一席位。

### 第三轮：公网交付和验收问题收口

本阶段实现记录见[第三阶段交接](online/phase-3-handoff.md)。源码、部署模板和管理运维动作已完成开发；域名、服务器容量、备份恢复和公网可玩性仍以用户实际部署验收为准。

1. 按用户实际服务器参数完成正式 Compose、域名/TLS、WSS 反代、数据库卷、迁移、备份、恢复、日志轮转、进程重启及启动文档。只开放必需端口，worker、数据库、调试端口及文件服务仅在内部网络。
2. 固定客户端、协议、卡牌/规则资源与 worker 构建标识；握手早期拒绝不兼容版本。滚动更新前停止新对局、排空活动实例；不能把升级强制踢下线包装成“可重连”。
3. 收口权限和资源限制：身份、房间管理、好友、邀请、席位、旁观、聊天均有服务器检查；过滤原型键和非法载荷，纯文本渲染玩家内容，日志脱敏。客户端不能请求执行任意代码或访问本地文件服务。
4. 完成维护模式、只读管理员状态接口/受保护管理工具、封禁/解封、房间/worker 异常关闭及审计记录；普通用户不可调用管理动作。
5. 完成可观测性：健康/就绪、在线会话、房间、排队、实例数、连接/恢复失败、请求延迟、worker 资源；使用 requestId、roomId、instanceId 关联日志，禁止记录密码、令牌、完整隐藏手牌。
6. 收口各平台 UI：桌面/手机、横竖屏、触控/键盘、空态、错误、加载、匹配、恢复、版本升级和离房；维持原画与统一主题。处理对局返回后遗留监听器、覆盖层和连接。
7. 用户执行公网矩阵，开发者根据实际日志和反馈修复本轮问题并补齐部署手册；这一轮含修复，不再单列“第四轮联调”。

## 8. 服务器信息、容量和未决项

当前只知道用户有服务器，系统、CPU、内存、域名、带宽、端口及预期并发尚未提供。先按单台 Linux、Docker Compose、同域 HTTPS/WSS、小规模邀请体验版设计；这不是已确认的环境。

后续所需信息：系统和架构、CPU/内存/磁盘、域名与 DNS 控制权、80/443 可达性、是否已有业务、预期同时在线人数和同时对局数。由用户提供接入方式时再确定具体部署，不在文档中索要或保存明文密码。

Chromium worker 单局内存与启动成本需要实际测量，不能用 WebSocket 最大连接数推导支持多少对局。调度器必须有最大实例数和启动并发限制；资源不足时拒绝/排队，不能持续创建进程直至服务器失效。现有数据库方案也不能被宣传为多节点高可用。

第一轮优先确定规则开放矩阵；服务器参数可以在第三轮正式部署前补齐，不阻塞 UI、协议和本地开发。域名、资源或用户验收未具备时，交付状态必须写“部署/验证待外部条件”，不追加开发轮数，也不宣称已达到最终目标。
