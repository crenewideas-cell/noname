## 1. 目标与完成边界

将 `temp/扩展UI/假装无敌完整包v2.0.4.zip` 中能够迁移的 UI 尽量完整迁移为独立组件库，同时完善现有 UI 工坊，使用户能在已有套装上仅通过界面配置选择、调整和组合这些部件。

“纯配置”指迁移完成后的使用体验：用户不需要写 JavaScript、编辑 JSON、手改 CSS、安装并开启旧扩展。开发者需要编写受信任展示适配和工坊功能，不能用当前配置格式的限制缩减迁移目标。

必须具备以下体验：

1. 打开任一现有套装或用户保存的搭配，选择某个具体部件，将来源切换为假装无敌组件库中的某个变体。
2. 可以只更换势力标识、卡牌特效或指示线，保留其他部件；动画不得被迫依附于假装无敌背景、布局或武将框。
3. “假装无敌默认组合”作为快捷预设存在，不能作为使用组件库的唯一入口。原包没有提供的部件沿用宿主搭配，并明确标明。
4. 各部件独立配置、预览、重置。保存、另存、重启、撤销、导出与重新导入均保留组合、参数和素材。
5. 如真似幻大厅、手杀标准 UI、十周年局内 UI、本体默认和颜色预设继续可用，旧的用户套装不因升级丢失。
6. 尽量完整覆盖来源 UI，不能只迁移三个示例。每个来源 UI 功能都必须有去向、证据或明确缺口。
7. UI 只改变展示，规则、合法操作、可见信息、AI、联机及胜负继续由当前本体负责。

“任意部件”指同类语义部件能独立替换；不是把结算页面塞进卡面槽。优先补齐布局适配，不能用“可能不兼容”笼统排除现有套装。确有结构依赖时必须给出具体原因、适配结果或明确组合要求，不强制全套启用。

## 5. 组件契约与配置体系

### 5.1 配置模型

基于当前工坊增量扩展，不另建第二套 UI 工坊。设计稿至少定义：组件类型、提供者 ID、变体 ID、类型化参数、媒体依赖、支持场景、定位锚点、默认值和宿主能力要求。最终字段名称由实施者结合现有代码确定，并写入开发文档。

如果需要格式 v2：显式版本化，提供 v1 → 新格式的幂等转换；保留原数据用于恢复，转换失败不能覆盖原记录。旧阅读器不能理解的新包应明确报告兼容版本，不把新版字段假装成 v1。

每个部件区分以下意图，不用一个空字符串混用所有语义：

- 保留当前部件：局部混搭操作不触碰它。
- 使用本体默认：明确移除该部件的提供者覆盖。
- 关闭可选效果：只关闭装饰/动画，不隐藏本体必要操作、信息或反馈。
- 选择组件变体：指定来源、素材及参数。

保存时记录确定的部件选择。需要继承时明确继承来源和解析方式，避免依赖当时全局扩展开关。组件参数随套装保存，不能藏在 `extension_假装无敌_*` 全局配置中导致分享失真。

混搭复制自定义素材数据，并保存内置提供者的稳定引用/版本要求。删除来源用户套装不应破坏已保存的搭配。重置某个部件只恢复该部件默认值，不清空其他部件。

### 5.2 所有权、优先级与既有套装适配

- 每个展示功能在当前场景只有一个明确生效来源，防止十周年动画与假装无敌动画同时播放。
- 从现有大部件解出细部件时，补齐旧提供者的启停粒度；不能只让新提供者遵守细分开关。
- 旧 `arena` 中的动画、声音、计时等选项要映射到相应细部件，保留原有启停偏好；新增部件的默认值不得重新打开用户原本关闭的效果。
- 大部件为默认组合提供值，用户明确的细部件选择优先；显式自定义素材和样式的优先级延续工坊约定。将冲突规则写清并测试，不以加载顺序决定。
- 实际画面、预览、保存、导出使用同一份解析后的有效配置。
- 大厅、联机管理页面、局内、资料页与结算的作用域明确；换局内字体/菜单不得意外修改所有页面。

### 5.3 定位与渲染

以当前宿主的头像、主副将、武将框、卡牌节点、手牌区、目标中心、对局容器等定义锚点，统一缩放和坐标系。允许局部偏移/缩放调节，但默认配置应可用，不能要求用户手调才能完成基本适配。

静态图片、CSS/DOM 装饰、图片指示线和 Spine 动画采用适合的受控渲染实现，共享资源加载与生命周期。参考已有皮肤运行时不意味着整份复制运行时；核对 Spine 3.6/4.0、JSON/二进制、贴图 alpha、atlas 多页、Worker/CSP 与浏览器支持后选择复用方案。

组件应能准备资源、挂载、接收配置、预览并释放；具体接口可沿用项目已有约定。应用整套仍可按当前工坊方式在大厅重载生效，不要求对局中热换整套。

## 6. 纯展示边界

1. 不加载原 ZIP 的 `extension.js`、`Function.js`、`CharacterCard.js` 作为 UI 运行入口，不重复注册已接入的清瑶武将卡牌。
2. 不修改技能/卡牌定义、AI、选择过滤、事件结果、玩家规则状态、联网流程、胜负；不注册“仅用于动画”的全局技能。
3. 不把旧规则挪到改名的“公共服务”中。缺少展示事件时在本体实际产生该状态的位置添加通用、非阻塞、只读可见快照。
4. 不覆盖 `Player.line`、`game.linexy` 或缩放方法来安装整套旧逻辑。完善当前通用指示线接口，保留拖拽调用所需的节点返回和更新约定，避免重复绘制。
5. 指示线/特效过滤采用声明式条件：事件种类、卡牌 ID、公开属性、公开数值范围、来源/目标等。起止点采用受支持锚点；不执行任意 `eval`、`new Function`、函数字符串或完成回调代码。
6. 连锁效果描述为受校验的效果引用，限制循环、深度和并发。动画回调只能推进展示序列，不推进游戏事件。
7. 本体节点和行为保留；资料页、换肤和合法操作经正式服务调用。不可用动作给出明确状态，不伪造成功。
8. 暗将、隐藏牌、观战、录像遵循本体可见性；皮肤不能查询隐藏数据来选图、算分或触发特效。扩展势力缺图用通用展示回退，不能改变势力。
9. 动画不阻塞游戏。关闭、加载失败、卸载、超时均不能改变对局；展示随机不消耗规则随机序列。
10. 结算读取本体结果和已有统计。旧评分不等于当前评分，缺少数据时标明不提供/待公共能力支持，不能显示捏造数据。

## 7. UI 工坊功能完善要求

- 增加可浏览的组件库：按分类列出组件与变体，支持名称检索、来源标识及当前选用状态。
- 保留“整套载入”，增加清晰的“只替换这个部件”操作，能在现有搭配上连续编辑。
- 参数控件来自组件声明的类型、范围和默认值；图片/音频/骨骼不都塞进通用 CSS 文本框。
- 指示线至少配置适用类型、外观变体、宽度/缩放、时长、透明度、起点、后续效果等实际支持项；音效独立开关，配置单位明确。
- 势力素材支持按 ID 映射、未知回退、主副将/场景区分；支持项目扩展势力，不仅六个常规势力。
- 卡牌匹配区分卡牌 ID、属性和必要公开状态，避免 `sha` 覆盖所有属性杀；保留隐藏牌和自带卡图的处理规则。
- 提供真实可运行的受信任组件预览：线从起点到目标、卡牌特效随卡牌节点、势力框展示未知/双将状态。参考图与实装预览明确区分。
- 预览模拟数据不执行游戏技能或来源脚本；预览资源、音频和画布在关闭时释放。
- 展示缺资源、版本不支持、配置冲突和应用失败的具体原因；回退不能伪装为成功还原。
- 保存/另存、导入不丢草稿、重复应用不制造副本、撤销、恢复本体等既有行为继续有效。

建议新增正式提供者目录 `apps/core/extension/ui/假装无敌UI/`；稳定提供者 ID 可使用 `jzwd`，最终以实施设计为准。不要占用现有规则集合下的“假装无敌”目录作为新 UI 入口。

建议包含现代薄入口、组件定义、纯展示代码、媒体、必要绘图库、`files.json`、来源/许可说明及迁移映射。原规则脚本、旧管理后台、解压工具可执行文件等不进入新提供者。保留作者和第三方许可，不把来源作者对代码的许可自动扩大到所有媒体。

资源处理要求：

- 导入来源时检查顶层目录、编码、重复/大小写冲突、路径穿越、总大小和单文件限制；不要覆盖正式目录后才分析。
- 建依赖闭包：骨骼 → atlas → 所有图集页，效果 → 后续/附加效果 → 音频/字体；不能只按入口文件扩展名复制。
- 用哈希识别重复资源，并记录逻辑引用；避免各组件各复制一整套数百 MiB 动画。
- 运行、日常构建、预览、导出不依赖 `temp`、原 ZIP 或开发电脑绝对路径。一次性来源转换脚本可以接收外部 ZIP，但正式构建不能强制再次读取它。
- 优先按选中组件/变体加载，限制缓存和同时播放数量，提供低性能模式；不能启动就预加载全部骨骼。
- 提供者路径、程序白名单、资源清单、工坊导入导出、联机 `ui-skins`、外观传递和客户端构建同步维护。
- 工坊导入只读取和校验数据，不执行 ZIP 中任意代码。缺少受信任提供者/版本时明确报依赖问题；若需通过扩展入口安装，记录受支持版本及安装步骤。
- 独立预设包与跨套装混搭包都必须包含所需资源和配置。提供者程序随包携带与宿主真正安装该程序是两件事，分别验证。
- 验证资源请求及包清单，不能让本机已有的提供者资源掩盖漏包。小部件导出尽量只带所需媒体；若当前机制必须携带整个提供者，披露体积并记录原因。

## 9. 分阶段实施与出口条件

| 阶段 | 工作 | 进入下一阶段的条件 |
| --- | --- | --- |
| A 基线与盘点 | 记录工作区、来源哈希；四路盘点；确认已迁入的规则与缺失资源 | 有功能覆盖清单、资源清单、缺口与依赖，不只给素材统计 |
| B 组件与兼容设计 | 定义细部件、参数、锚点、所有权、旧格式转换与导入依赖 | 设计能表达三种不同来源的混搭，且旧套装行为有迁移映射 |
| C 最小完整链路 | 选择一个图片指示线和一个势力部件，完成选择→预览→保存→应用→导出→导入 | 在至少两个不同宿主搭配中真正生效，切回后无残留 |
| D 扩展静态部件 | 迁移包内卡图、字体、边框、体力、按钮/菜单等可用素材 | 每项进入功能清单并支持独立配置；说明包外卡面来源 |
| E 动态与演出 | 骨骼线、卡牌/技能/装备、状态、开战/连杀/互动、声音 | 按事件播放、版本适配、无重复效果、无规则依赖；关闭/失败可继续游戏 |
| F 页面与结算 | 资料/换肤/结果/MVP 的可迁移展示；补齐遗漏项 | 使用本体服务与结果；缺来源或数据能力的项明确，不能虚构 |
| G 分享与多端 | 混搭包、自定义资源、旧包升级、独立联机窗口、客户端构建 | 实际往返、资源闭包和外观恢复有证据 |

这些阶段用于组织持续实施，不表示做完 C 就可以结束。真正缺少来源时及时列明所需文件，并继续完成不依赖它的工作，不以资源不完整为由停掉全部迁移。

## 10. 验收矩阵

### 10.1 部件独立性与旧数据

- 每个迁入部件至少在两种不同基础搭配上完成单独替换，其中一种为本体默认或颜色预设。
- 全部现有套装类别各完成至少一个真实混搭；按共享 DOM/布局归类增加边界组合，不要求穷举所有排列，也不能只验证假装无敌整套。
- 必测：如真似幻大厅＋十周年局内＋假装无敌势力/指示线；手杀布局＋假装无敌卡牌特效＋原卡面；默认布局＋假装无敌结算展示。
- 只选动画不要求切换背景/布局；更换势力不要求更换武将框；攻击线与拖拽行为分别验证。
- v1 内置、用户自定义、缺省字段、显式关闭、混合 runtime、当前/撤销引用、重复导入 ID、名称相同不同内容均有数据兼容检查。
- 保存、重启、另存、删除来源搭配、导出再导入后，部件选择/参数/素材一致；旧库升级失败不破坏原始数据。

### 10.2 视觉与对局行为

- 主要模式、不同人数、国战双将、暗将/揭示、扩展势力、属性杀、多属性/虚拟牌、装备/判定/标记状态正确。
- 图片指示线与骨骼线、单/多目标、缩放、主副将和手牌区起点、后续效果核对；不重复叠线、不丢拖拽反馈。
- 桌面和移动横屏、窄窗口、不同 DPR 与缩放下不遮挡合法操作。静态图不能证明动效已完成。
- 同一初始状态、可控随机源和相同合法输入下，对比默认外观与混搭外观的规则结果；不靠视觉近似证明规则隔离。
- 强制资源失败/超时、关闭动画、切换、退出、重新进入、重连均不改变玩法，不残留画布/订阅/音频。
- 音效与动画不会双播；低性能降级有明确效果；记录实际设备、加载耗时、帧时间及资源使用，不编造性能门槛通过结论。

### 10.3 分享、多端与来源独立性

- 使用真实工坊 UI 完成导出→干净用户配置导入→应用→对局；读写器清单往返仅算一层检查。
- 至少交付假装无敌默认组合包和两个不同底座的混搭包，其中一个包含用户自定义参数/素材。
- 在无开发来源可访问的测试环境中验证资源闭合，不能仅断开网络而仍读取本机旧目录。
- 独立联机窗口正确传递所有新部件与参数，重连不重播一次性开战/结算，服务器不加载展示程序。
- Web、Electron、Android 分别记录验证状态；Web 通过不能替代另外两端。平台不可用时标未验证，保留可复现步骤。

证据记录实际日期、工作区版本/相关变更、命令、环境、结果和文件路径。原包截图、历史报告、静态搜索、素材文件存在均不能单独充当实装验收。

## 11. 清理范围与执行纪律

本任务授权后的实施清理仅针对本任务引入或替换、且确认无用的程序、资源、临时输出和死引用。不要照搬旧十周年手册要求清理其他 UI 的历史目录，也不清除现有清瑶规则集合中的文件来证明“纯 UI”。

清理前追踪运行、动态路径、CSS、图集、生成和打包引用。Windows 递归操作先校验解析后的绝对路径位于明确任务目录，使用单一 PowerShell 流程和 `-LiteralPath`。不自动删除原 ZIP、整个 `temp`、用户数据或无关产物，不执行全仓库清理或重置。

实际实施时保护已有及并行修改；本手册编写时发现 `apps/core/extension/packs/梦渊涵花/character/skill.js` 有已有修改，仅作提醒，执行时重新检查。文档不授权远端发布、部署、推送或操作真实联机房间。

可直接推进可逆且必要的开发、针对性测试、本地构建和导出，不逐阶段索要重复确认。缺必需来源或业务语义不明时提出具体问题，同时继续独立工作。不得因为要验收而运行原包混淆入口或携带旧规则来“还原”。
