## 1. 结论与使用方法

现有问题需要同时解决三个层面：**进入界面前加载了过多内容、首次交互时集中执行了大量工作、运行期间渲染与资源管理缺乏统一预算**。仅增加启动提示、延长超时、压缩几张图片，无法达到全程流畅的目标。

建议依次实施：建立基线 → 减少首屏必需内容 → 优化真实选将分页与首次开局工作 → 治理帧耗时和资源生命周期 → 建立持续性能验收。

本次最值得优先处理的证据如下：

| 发现 | 对用户体验的影响 | 首要动作 |
| --- | --- | --- |
| 大厅显示前，等待扩展导入和 `all.characters / all.cards` 脚本导入 | 首次访问的等待范围远大于“显示主界面”所需 | 分离轻量入口、目录数据与对局运行代码 |
| “分支武将”静态导入 71 个包，再在浏览器中创建包、扫描技能依赖 | 启用该扩展后，增加启动下载、解析和同步计算 | 生成构建期依赖清单，拆分按需加载单元 |
| 启动主动加载 `xinwei`、`shousha`；两文件合计约 12.09 MiB | 即使不阻塞文字显示，也可能争用首屏网络与解码资源 | 按当前界面选择字体，做字体子集与分片 |
| 选将分页先创建全部按钮，再隐藏其他页 | 显示数量减少，但首次创建成本和大量遍历仍存在 | 先对数据分页，再创建当前页按钮 |
| `lib.onfree` 延后执行菜单、按钮初始化；回调内部仍可长时间同步执行 | 卡顿可能从启动转移到选将、第一回合 | 分预算执行，用户操作期间暂停非必要后台任务 |
| 手牌排布循环中写样式后读取计算样式或尺寸 | 存在反复样式计算、布局的风险 | 对同一帧合并更新，先读后写 |
| 普通构建保留模块，核心关闭 tree-shaking；构建使用固定文件名 | 可能增加模块请求、解析和缓存校验成本 | 按构建渠道评估分包，建立版本化资源策略 |

**一个已验证的关键约束：不能直接全局开启 JavaScript 压缩。** 本工程旧式技能依赖函数源码中的 `"step 0" / "step 1"` 标记。用仓库已安装的 Terser 对最小示例进行压缩，标记被移除。必须先完成构建语义保护，再对相关代码启用压缩，见第 6.7 节。

本手册中的“流畅”指在约定的设备、网络、模式和扩展规模内达到第 4 节的指标，并在资源失败时保持可操作和可恢复。不能用一份静态分析保证任何硬件、任何网络、任意扩展都绝不卡顿。

## 2. 工程运行方式及现有启动链路

### 2.1 必须先区分访问的是哪种程序

| 运行方式 | 代码入口与配置 | 分析注意事项 |
| --- | --- | --- |
| 本地网页开发 | 根目录 `pnpm dev` → `scripts/dev.ts` → Vite，默认 `127.0.0.1:8081`；文件服务 8089 | 首次模块转换、依赖预构建、HMR 影响明显；不能作为生产性能验收结果 |
| 完整静态构建 | `scripts/build.ts`、`apps/core/scripts/build.ts`；根目录 `pnpm build`、`pnpm serve` | 包含扩展、图片、音频；普通核心构建 `preserveModules: true` |
| 公共联机客户端 | `scripts/build-online.ts --client`、`scripts/online-artifacts.ts` | `NONAME_PUBLIC_BUILD=1` 时核心合并策略不同，公共客户端跳过普通扩展加载 |
| 联机服务/托管对局 | `packages/server`、`packages/game-host`、`deploy/online` | 网络等待、服务端排队与客户端渲染需要分开计时 |

`deploy/online/Caddyfile` 当前为 API/WebSocket 代理，其兜底返回提示使用客户端下载的 404；其中的压缩配置不能据此认定用户访问的游戏静态站点已经开启压缩。`Assets.Caddyfile` 对资源设置 `no-cache`，但没有声明 `encode`。最终以实际承载网页的响应头为准。

### 2.2 当前主要启动顺序

```text
index.html：立即显示启动提示
  ↓ 加载 noname/entry.ts 的静态依赖图
noname.js → lib / game / get / ui / ai / 元素类等
  ↓ 平台 preload、build-info、首次使用确认
boot()
  ↓ polyfill、配置和存储、兼容层、沙盒初始化
  ↓ CSS、package 清单、字体请求、update 信息
  ↓ getExtensionList：登记/恢复，必要时发现新扩展
  ↓ 顺序 importExtension；等待扩展异步导入
  ↓ 导入 all.cards / all.characters，rank / replace / perfectPairs
  ↓ 等待导入完成、onload、背景和样式准备
显示 splash / EntryShell 大厅（非直接开局时）
  ↓ 用户选择模式，importMode
  ↓ loadMode、loadCharacter、loadCard、loadExtension.content
  ↓ 牌面预取、ui.create.arena、创建模式启动事件
  ↓ onprepare 等待、事件循环、模式选将、首轮对局
  ↘ onfree 延后的菜单、按钮与其他准备任务
```

关键证据：`apps/core/noname/init/index.ts` 中，扩展导入循环约在 317 行，卡牌/武将导入约在 389 行，等待约在 399 行，大厅初始化约在 542 行，对局界面创建约在 676 行。

`all.characters` 与 `config.characters` 不是同一个列表：前者参与导入，后者参与启用/规则筛选。当前 `game/package.js` 登记 26 个本体武将包、9 个卡牌包；默认配置启用 23 个武将包、2 个卡牌包。实际导入列表还受隐藏设置、扩展注册和联机分支影响，不能仅用“启用包数”推断请求量。

## 4. 将“全程流畅”转为可验收指标

### 4.1 测试设备与场景

先确认主要使用设备的具体型号，至少固定以下档位；首次基线后记录实际硬件、浏览器版本、视口和显示刷新率，不在不同设备间混算百分位。

| 档位 | 建议测试条件 | 用途 |
| --- | --- | --- |
| D 桌面 | 用户实际桌面设备，60 Hz 口径，无 CPU 限速；20 Mbps 下载、40 ms RTT | 主要流畅度目标 |
| M 移动 | 一台真实中档 Android 设备，10 Mbps、80 ms RTT | 触控、内存、图片解码、热稳定性 |
| L 弱设备/弱网 | 指定较旧设备，4 Mbps、150 ms RTT；可辅以桌面 4 倍 CPU 限速排查 | 可用性、降级和最大等待控制 |
| S Safari | 最低支持版本能力检查及一台实际目标 iOS/macOS 设备 | 字体、视频、调度 API 的兼容性 |

桌面 CPU 限速不能替代真实手机。当前工程声明兼容 Chromium ≥91、Safari ≥16.4；较新的 `scheduler.yield`、观察器条目等必须能力检测并提供回退。

每档区分：浏览器冷缓存/热缓存、服务器冷启动/预热、首次登记/旧存档、精简包/用户正常扩展组合/完整支持组合。全扩展压力用例只在明确兼容的组合上执行。

### 4.2 建议预算 v1（待基线确认）

| 指标 | D 桌面 | M 移动 | L 弱网/弱设备 |
| --- | --- | --- | --- |
| 导航到大厅可交互，冷缓存 p95 | ≤3 秒 | ≤5 秒 | ≤8 秒且持续显示真实进度 |
| 导航到大厅可交互，热缓存 p95 | ≤1.5 秒 | ≤2.5 秒 | ≤4 秒 |
| 点击模式到候选可操作，所需包已就绪，p95 | ≤300 ms | ≤500 ms | ≤1 秒 |
| 点击模式到候选可操作，包冷加载，p95 | ≤3 秒 | ≤5 秒 | ≤8 秒或明确提供重试/返回 |
| 换页、筛选、选择反馈，p95 / p99 | ≤100 / 200 ms | ≤150 / 250 ms | ≤250 / 500 ms |
| 前台稳定交互 INP，现场访问 p75 | ≤200 ms | ≤200 ms | 单独跟踪并说明降级档位 |
| 候选页面图片缺失时 | 名称、边框、选择操作立即可用 | 同左 | 同左 |
| 候选缩略图可见，资源命中后 p95 | ≤150 ms | ≤250 ms | ≤500 ms |
| 连续交互时大于 50 ms 的长任务 | 持续降低，目标无重复出现的长任务 | 同左 | 降级后无持续阻塞 |
| 60 Hz 前台帧间隔 | p95 ≤20 ms，超过 33.3 ms 的样本 <1% | p95 ≤25 ms，超过 33.3 ms 的样本 <3% | 允许显式低特效档，避免连续 >100 ms 停顿 |
| 同页关闭重开面板 20 次后内存 | GC 后相对稳定基线增长 ≤10%，且无持续上升趋势 | 同左 | 同左 |
| 必需脚本失败 | 有明确错误、可重试或返回；不可假装就绪 | 同左 | 同左 |

以上“包冷加载”目标可能需要较深的包拆分才能达到，不能把进度条显示时间算作候选已可操作。对局主动设计的动画、出牌思考时间与网络等待应另列，不计入纯 UI 处理耗时，但其间输入仍应有反馈。

INP 的 200 ms 建议来自 [web.dev 的 INP 优化说明](https://web.dev/articles/optimize-inp)。本表其他阈值是项目建议，不是浏览器规范。平均 FPS 不足以证明流畅，必须观察长尾卡顿、掉帧和交互响应。

建议的首屏资源预算：轻量大厅 JS 传输量 ≤500 KiB、总关键资源 ≤1 MiB、关键自定义字体 ≤200 KiB、关键请求 ≤30 个。对“大厅已可操作”这个阶段统计；游戏运行包另建预算。阈值不适用于把整个引擎都视为首屏必要内容的现状。

## 5. 先建立能定位原因的测量体系

### 5.1 埋点设计

入口的最早测量代码放在 HTML 或真正的轻量入口，不能只放在 `entry.ts` 函数体中：ESM 静态依赖执行发生在其函数体之前，否则会漏掉最前面的模块开销。

建议实现可关闭的 `noname/perf` 模块，记录 `performance.mark/measure`，按 `build / session / mode / extension / actionId` 归类。采集器只保留有限环形缓冲，不同步输出大量日志。

| 阶段 | 起止点 | 目的 |
| --- | --- | --- |
| `boot.total` | Navigation Timing 的导航起点 → 大厅完成可操作渲染 | 真实首次进入体验 |
| `boot.entry-body` | `entry.ts` 函数体开始 | 区分前置模块图与 boot 函数本身 |
| `boot.config / sandbox / css` | 对应 await 前后 | 定位串行阶段 |
| `extension.import:<id>` | `importExtension` 前后 | 含下载、解析、工厂及其等待；不能直接当作纯 CPU |
| `extension.content:<id>` | `loadExtension` 前后 | 启用扩展初始化负担 |
| `pack.import:<id>` | 武将/卡牌导入前后 | 识别请求瀑布、包边界和异常 |
| `boot.register / finishCards / arena` | 注册与归一化、界面创建前后 | 主线程集中工作 |
| `choose.data / choose.dom / choose.presented` | 生成候选 → 创建节点 → 可见并可操作 | 分离选人数据、DOM、呈现 |
| `choose.images-visible` | 当前可见候选原图或缩略图就绪 | 独立于可操作时间 |
| `interaction:<actionId>` | 输入事件时间 → 对应反馈的后续呈现机会 | 捕捉筛选、换页、选将、手牌交互 |
| `match.first-action` | 确认选将 → 本地首个合法操作可用 | 不包括他人选将或主动思考等待 |
| `event.compile:<skill>` | 编译命中/未命中、编译耗时 | 区分首次技能卡顿与重复执行成本 |

调试版本可用连续两次 `requestAnimationFrame` 作为“经历了一次呈现机会”的近似；它不是精确 paint 证明，也不代表页面已准备好接收所有操作。自动化需要同时检查按钮启用状态和关键数据完整性。

### 5.2 采集内容与复现规则

1. 在隔离浏览器配置或独立测试 origin 中操作，使用保存的测试存档快照。不要清空用户原始 origin 的存档，也不要擅自改变启用扩展。
2. 固定 commit、构建渠道、配置、候选规模和操作步骤。记录冷/热浏览器缓存、冷/热服务端、屏幕刷新率和是否接电。
3. Network 记录请求数量、域名、TTFB、排队时间、传输/解码大小、失败与重试、缓存来源；导出 HAR。
4. Performance 分别录制“导航到大厅”“点模式到首回合”“搜索换页与手牌连点”，保留截图轨迹和 CPU 栈。
5. 看 Bottom-up 的 Self time 与 Total time，按脚本、样式、布局、绘制、GC 分组，不只看最长文件名。
6. 用 `PerformanceObserver` 采集支持的 `longtask`、`event` 等条目；不支持则用 DevTools 录制。`event` duration 样本不直接等于规范 INP，INP 使用正确聚合实现。
7. 资源条目可能超出默认缓冲；增大并定期消费缓冲。跨域详细计时需要资源端正确的 `Timing-Allow-Origin`，否则不能将 0 字段解释为“免费”。
8. 每个主要启动条件至少 20 次用于初步比较；发布阶段累计 ≥100 次，报告 p50/p95 与最慢样本。交互 p99 至少收集 1,000 个同类操作样本，避免用 10 次测量报告可信 p99。
9. 前台流畅度采样剔除后台标签页；主线程 rAF 间隔、合成器掉帧和视频 dropped frames 分开记录。
10. 跑 60 分钟主要对局/重开循环；每 5 分钟观察堆、DOM、监听器、视频和音频数量。返回大厅如果会整页重载，应单独标记，不能据此证明同页面板没有泄漏。

DevTools 的 CPU、网络及栈定位方法见 [Chrome Performance 面板参考](https://developer.chrome.com/docs/devtools/performance/reference)。日志里不要保存访问令牌、完整个人配置或私人聊天数据。

## 6. 具体优化开发方案

### 6.1 PERF-01：建立轻量入口，拆开“看目录”和“运行游戏”〔P1，已证实〕

涉及：`noname/entry.ts`、`noname/init/index.ts`、`noname.js`、`noname/online/ui/EntryShell.vue`、`noname/init/onload/default-splash.ts`。

当前大厅本身虽已动态导入，但执行时点在扩展和本体包导入之后，而且组件仍依赖 `noname`。仅把 `splash.init()` 向前挪会遇到尚未初始化的 `lib`、扩展模式和配置依赖。

实施步骤：

1. 生成轻量模式/扩展目录清单，包含 id、名称、图标、可用状态、运行入口、依赖版本。入口页只读取清单与最少设置。
2. 新建不静态导入 `noname.js` 的入口展示层；通过适配器向旧引擎提交“选择模式/打开设置/联机”等意图。证明入口依赖图不再回引整个引擎。
3. 保持旧入口可切换；将引擎初始化作为一个显式阶段，先显示可操作主界面，再按用户意图准备运行包。
4. 初次不知道扩展动态模式信息时，使用构建清单；无法静态描述的旧扩展进入兼容准备路径，并显示真实状态。不可静默丢失扩展模式入口。
5. 以用户预计下一步为基础预取少量运行包，限制带宽和并发；不得在后台立即全量加载，把首屏加速换成点击后卡顿。
6. 进入对局前确认依赖闭包、注册和必要 UI 都已就绪。功能页仍可浏览目录，但未就绪的开局动作要明确等待与返回。

验收：大厅准备时不下载无关技能、皮肤和扩展运行文件；冷/热导航与首次模式点击均达到预算；直接开局、回放、返回大厅和联机跳转不丢失行为。

### 6.2 PERF-02：扩展依赖与包加载治理〔P1，已证实〕

涉及：`noname/init/import.ts`、`loading.ts`、`organizedExtensions.ts`、`extension/分支武将/extension.js`、`catalog.js`、`asset-map.js`、`scripts/mergeBranchCharacters.ts`。

当前分支武将入口静态导入 `catalog` 和资源映射，随后 `packs.map(pack => pack.create(...args))` 创建所有来源数据；`tokens()` 遍历对象并把函数转为字符串，用正则收集技能/卡牌依赖。`content()` 中继续遍历角色、翻译和依赖；角色过滤器还会重复运行 `skillProblems()`。

实施步骤：

1. 在现有生成脚本中生成角色元数据、资源子映射、技能/卡牌依赖关系及来源信息。优先 AST/明确声明；对动态拼接、运行时注入和外部扩展依赖保留显式清单或兼容回退。
2. 用构建期已知数据生成“本场候选 + 衍生/召唤 + 共享技能 + 全局规则”的依赖闭包。按场景或来源拆包，不机械地一武将一请求。
3. 将“下载”“执行/注册”“激活”区分开。**并行 import 会执行顶层代码**，不是纯下载；有副作用的旧扩展不能一律 `Promise.all`。
4. 对声明为无副作用的数据模块可并行获取、固定拓扑顺序注册；旧扩展继续兼容顺序。名将杀 `main/runtime.js` 的固定顺序合并可作为局部参考，但需先确认其模块是否纯数据。
5. 登记恢复保留幂等语义。关闭扩展目前也可能顺序读取 `info.json`，可由清单提供元数据，避免拖慢所有扩展的队列。
6. 目录扫描保留显式“发现/刷新扩展”能力；安装清单未变时避免重复探测。无法确认外部手动安装变化时，不直接删除扫描能力。
7. 缓存技能可用性和目录结果时，键包括引擎/扩展 build、启用集、模式和注册版本；全局依赖发生变化时失效。不能永久缓存“缺失”，阻碍后加载扩展恢复。

验收：用户正常启用集、经典包、全支持包、旧扩展组合结果一致；共享/继承/子技能、重名覆盖顺序、全局技能、召唤与动态获得技能无缺失。报告实际加载包数、注册耗时和长任务变化，不仅报告文件变小。

### 6.3 PERF-03：字体与首屏媒体减负〔P1，已证实〕

涉及：`noname/init/index.ts:198` 附近、`font/`、`layout/`、`theme/`、扩展字体声明。

当前 `activeFonts` 固定包含 `xinwei` 与 `shousha`。即使已经 `font-display: swap`，主动 `document.fonts.load()` 仍会请求匹配字体。传入“情思杀闪桃123”只筛选匹配字面，不会把一个 7.49 MiB 字体文件自动裁成几个字，参见 [FontFaceSet.load 文档](https://developer.mozilla.org/en-US/docs/Web/API/FontFaceSet/load)。

实施步骤：

1. 首屏使用当前展示风格真正需要的字体；未选中的风格不主动加载。核心提示、菜单和候选名称始终有可读系统字体回退。
2. 构建期生成常用 UI 字符小子集，再以 `unicode-range` 分片提供正文和罕见武将姓名字符；分片必须覆盖扩展文本，不做会丢字的永久裁剪。
3. 保留字号、行高和容器尺寸，控制字体替换后的布局移动；字体加载后只触发必要的一次排布。
4. 原图、缩略图、卡面与大屏详情分开生成尺寸。先按实际 CSS 尺寸 × DPR 确定候选图规格，再比较 WebP/AVIF/JPEG 的体积、解码和兼容性。
5. 不先预取所有高清背景和音视频。字体、首屏静态图片、候选图的优先级高于装饰视频。

验收：冷缓存请求中不出现未选风格的大字体；中文、拼音、生僻名、花色点数可读；图片失败不挡住选择；对比传输量、解码时间和 CLS。字体已经是 WOFF2，不应把再压缩传输当作主要收益。

### 6.4 PERF-04：人物列表做真实分页，独立选择状态〔P1，已证实〕

涉及：`noname/ui/create/index.js:1146` 的 `characterDialog()`、约 1890 行的 `dialog.add([list, ...])`、1916 行分页逻辑、3617 行 `buttons()`，以及 `library/element/dialog.js`、`game/check.js`。

当前 `buttons()` 已使用 `DocumentFragment`，所以“加一个 fragment”不是新增方案。真正问题是完整创建列表和分页后全表改 class；`queueMicrotask` 中建立技能搜索索引也没有给浏览器提供绘制机会。

实施步骤：

1. 以角色 id 与轻量元数据为源，先计算筛选/排序结果，再从结果中切当前页。优先实现显式分页，后续视体验需要评估虚拟滚动。
2. 选中角色、禁用原因、焦点和多选状态保存在数据层，不依赖屏幕外 DOM 是否存在。
3. 为新目录组件提供适配接口。旧调用方与 `game.check()` 会访问 `dialog.buttons`，不能直接把全量按钮替换成当前页而不检查其选择/AI语义。
4. 初期只迁移自由选将、武将浏览和设置目录；普通开局少量候选与技能 `chooseButton` 保持原接口，逐步适配。
5. 搜索索引按包版本生成/缓存；索引较大时在 Worker 或有预算的任务中构建。查询只返回 id，主线程只更新当前页。保留现有正则搜索时处理非法表达式和执行成本，必要时对普通文本搜索提供明确入口。
6. 为索引和搜索结果缓存设置容量与失效策略。现有 `#skillRegsCache` 是 Map，源码未体现查询容量限制；后续反复搜索及运行时增包需一起验证。
7. 当前页之外最多预取相邻页图片，切页取消过期任务。关闭对话框释放节点、观察器和监听器。

验收：100/1,000/5,000 角色目录的首次打开、查询、翻页分别测量；比如设置每页 48 项时，实际创建的角色按钮不超过当前页及明确的复用缓冲，不能仅检查 `display:none` 后的可见数。选择顺序、跨页选择、禁将、收藏、键盘焦点及旧扩展自定义按钮不回归。

公共联机的 `CharacterPoolEditor.vue` 已把显示结果限制为前 100 项，不能套用“全量 DOM”结论；但 `onMounted` 会补导入缺失的全部联机包来读取目录。应改为独立元数据接口/文件，避免看目录需要加载技能实现。

### 6.5 PERF-05：拆分首局同步工作，避免后台任务撞上交互〔P1，代码已证实，耗时待测〕

涉及：`noname/library/init/index.js:97` 的 `onfree()`、`noname/ui/create/index.js:3140` 的菜单准备、`buttons()` 的 `prebutton` 激活、`noname/game/index.js:8976` 的 `finishCards()`、事件编译器。

`onfree()` 当前先等 500 ms，再每 100 ms 执行一个回调。回调本身可以一次创建完整菜单或激活全部预备按钮；计时器推迟执行不等于执行过程不会卡顿。`finishCards()` 也会同步遍历所有卡牌和技能。

实施步骤：

1. 标出各回调耗时、调用次数、首次/再次命中。用户必须使用的内容优先，其余任务按页面生命周期调度。
2. 菜单按实际打开页面初始化。扩展菜单已存在惰性路径的部分保留，不重复构造整套 UI。
3. 安全批处理的工作采用 4–8 ms 时间预算，超过预算在任务间主动让出；记录并限制积压队列。
4. `Promise.resolve()` 和 `queueMicrotask()` 不能作为“已让浏览器绘制”的手段；`requestAnimationFrame` 内也不能放入完整重计算。优先能力检测后的 `scheduler.yield()`，回退到下一任务；空闲任务提供超时和取消机制。
5. 对 `finishCards`、包注册、事件处理等逻辑，先证明安全边界：中间状态不能被输入事件、AI或联机消息观察。必要时用显式 preparing 状态，在完成提交后开放对局操作。
6. 保留 `ContentCompiler` 的 WeakMap 缓存，先测首次编译未命中。只在确认必要后预编译本场相关技能，不启动即编译所有技能。注意动态创建新函数会避开按对象身份缓存。

任务分拆方法见 [web.dev 长任务优化](https://web.dev/articles/optimize-long-tasks)；`requestIdleCallback` 的能力与超时约束见 [MDN 文档](https://developer.mozilla.org/en-US/docs/Web/API/Window/requestIdleCallback)。这些 API 需要按最低支持浏览器回退。

验收：选将出现后的 10 秒内不再集中发生菜单/索引长任务；首次技能和第二次技能分开对比；取消准备、快速切模式与返回大厅无残留任务。

### 6.6 PERF-06：统一资源队列，保留同步图片接口〔P2，已证实〕

涉及：`noname/util/imageReady.ts`、`noname/init/polyfill.ts:272`、角色/卡牌绘制与红楼幻境资源管理。

当前 `warmImages()` 是“每次调用最多两个循环”，并非跨整个应用的全局并发上限；Promise 缓存也不是图片解码内存池。当前主要调用点为牌堆预取，未来扩大复用时不能把局部限制当作全局保证。

实施步骤：

1. 建立共享队列，按“当前可见资源 → 当前候选/牌面 → 下一步可能使用 → 装饰资源”排序，初始以 2–4 个可调任务槽试验。
2. 按 URL+版本去重；记录排队、下载、解码、失败原因。超时、重试和负缓存要有上限，避免资源不存在时重复探测。
3. 场景切换时从队列移除过期工作；已完成结果可以复用。使用 fetch 的路径通过 AbortController 取消；原生 Image/媒体取消语义另做兼容验证。
4. 严格保留 `setBackgroundImage()` 同步写样式和返回节点的契约，预取仅改善缓存。不能等待 `decode()` 后才写背景，否则选将节点复制可能重新出现空图。
5. 解码预算看像素而非文件大小：一张 2048×2048 的 RGBA 位图仅像素存储约 16 MiB，还未含浏览器/GPU开销。大图只在详情需要时加载。
6. 图片缓存不能无限持有 `ImageBitmap`、DOM 或 Blob URL；替换/关闭时 close/revoke，考虑失败重试和共享引用计数。

验收：重复打开和切页不出现重复请求风暴；装饰资源不会长期占满候选资源队列；慢图/坏图不冻结操作；连续 20 次开关面板后资源数量回到稳定范围。

### 6.7 PERF-07：构建与 HTTP 分发优化，先保护运行语义〔P1/P2，已证实〕

涉及：`apps/core/scripts/build.ts:150`、`scripts/build.ts`、`scripts/online-artifacts.ts`、`packages/fs/src/index.ts:71`、`deploy/online/Assets.Caddyfile`。

当前核心 `minify:false / treeshake:false`；独立包 `minify:false / treeshake:true`；普通核心保留模块、公共联机核心合并模块；输出文件名不带 hash。不能把所有渠道概括成“未打包”。

**构建兼容性先决条件**

`StepCompiler.ts:68` 用正则查找步骤字符串；114 行附近使用 `Function.prototype.toString` 或沙盒反编译获取函数文本。本地 Terser 最小实验为：

```js
// 输入
export function skill() {
  "step 0";
  player.draw();
  "step 1";
  player.recover();
}

// 默认 module 压缩输出（已在本仓库依赖中验证）
export function skill(){player.draw(),player.recover()}
```

这证明默认压缩可以删掉步骤标记，不证明任何特定生产技能已经因此出错。构建改革必须保护步骤标记、跨步骤变量、源码反射、动态翻译和扩展钩子。仅 `keep_fnames` 不足以保护这些字符串。

建议顺序：

1. 先对真正的静态资源服务启用 gzip/Brotli 或当前服务器支持的压缩。这不改 JS 源码语义；用响应头和实际下载大小验证，不改 API/WebSocket 缓存策略。
2. 产出每个入口的实际静态/动态依赖与原始/压缩体积报告。保留受控可用的 source map 以便定位。
3. 对纯 UI、第三方稳定模块等经过审计的范围做压缩；旧式技能先排除，或在构建期转换为保留语义的显式事件结构后再压缩。
4. tree-shaking 从明确无副作用模块逐步启用；不要全仓标 `sideEffects:false`。`noname.js` 的循环依赖与全局注册顺序必须保持。
5. 对普通静态构建评估合理合并；保留动态武将、模式和扩展的契约入口，避免另一个巨型 bundle。公共联机已经 `preserveModules:false`，需单独评估现有 chunk 大小。
6. 审计入口 `core-js-bundle`、完整 Vue 浏览器构建和 `get/index.js` 的拼音、JSZip静态依赖。对异步工具场景惰性加载；存在同步 API 或扩展运行时模板的依赖不能直接删掉或改 async。
7. 引入内容 hash 或不可变版本目录，HTML/manifest 指向同一 build。现有根路径动态 import 和 import map 要一起改，不能只给 chunk 改名。
8. 检查 `scripts/build.ts` 的子进程状态：当前调用后未检查 `spawnSync` 的失败状态便继续合并，可能形成旧新混杂产物。发布流水线必须失败即停止，产物完整后再切换。

缓存规则建议：

| 内容 | 策略 | 验证 |
| --- | --- | --- |
| HTML、可变 manifest | `no-cache` + ETag/Last-Modified | 允许存储但每次使用前校验；不是 `no-store` |
| 带内容 hash/不可变 build 路径的 JS、CSS、图片、字体 | `public, max-age=31536000, immutable` | URL 变化代表内容变化；旧版本资源保留用于进行中对局 |
| 无版本固定路径资源 | 条件缓存或短缓存 | 不可直接设一年 immutable，否则更新后混版本 |
| 登录、账户、实时 API、WebSocket | 保留其原有不可缓存语义 | 不将静态缓存规则扩展到私人数据与协议 |

HTTP 缓存语义见 [MDN HTTP caching](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Caching)。当前文件服务 `maxAge:0` 仍可能条件缓存；`Assets.Caddyfile` 的 `no-cache` 不代表一定重新传输完整文件。

本仓库为 Vite 7.x，实施参数以锁文件与安装版本为准；[Vite 构建说明](https://vite.dev/guide/build) 可用于理解资源路径和分块，不能直接套用未来主版本的压缩默认值。CDN、HTTP/2/3 和 Service Worker 均在确认网络瓶颈后引入；不要把整个扩展库作为离线预缓存清单。

验收：用**实际压缩后的构建产物**跑旧步骤技能、async技能、继承技能、回放、扩展加载与联机回归；冷/热缓存、发布中旧页面继续运行、回滚和丢失 chunk 均有测试。构建成功不等于行为正确。

### 6.8 PERF-08：手牌与对局 UI 合并更新〔P2，结构已证实，收益待测〕

涉及：`noname/ui/index.js:220` 的 `refresh()`、447 行的 `updatehl()`、565 行的 `updateh()`；`library/element/player.js`、`card.js` 和样式目录。

`refresh()` 读取 computed opacity；`updatehl()` 在循环中更新 transform、刷新样式，部分分支随后读取 `offsetWidth`。这证明存在读写交错，是否强制布局及其时间须看 trace，不能把每次 computed style 读取都算作完整重排。

实施步骤：

1. 同一帧多次 `updatehl()` 合并为一次，记录脏区域；引擎逻辑状态保持即时提交。
2. 批量读取容器和卡牌尺寸、计算排布，再批量写样式。尺寸缓存通过 ResizeObserver/窗口缩放/字体变化失效。
3. 保留动画的起始状态与结束状态边界。不要批量删除 `ui.refresh`，其部分调用用于确保动画切换生效；先迁移局部到明确动画机制并做视觉回归。
4. 在热点样式中将 `transition:all` 收窄到实际动画属性；按绘制轨迹检查阴影、滤镜、遮罩等成本，不全局修改美术效果。
5. 合理使用 CSS containment；不要在未验证尺寸和定位关系时给整个 arena 强加 containment，也不要给所有元素永久 `will-change`。

验收：同一输入周期的排布调用次数下降；Style/Layout 时间与慢帧减少；手牌展开、拖拽、多选、判定区、触屏横竖屏、缩放和扩展布局一致。

### 6.9 PERF-09：AI、规则过滤和首次技能执行〔P2，待实测〕

涉及：`noname/ai/basic.js`、`noname/game/check.js`、`noname/game/index.js` 的 `checkMod()`、`library/element/gameEvent.ts` 与技能文件。

`chooseButton` 可重复评分并调用 `game.check()`；`processSelection` 每次遍历候选、调用过滤与 hook；`checkMod` 涉及技能扩展和排序。已有缓存应先看命中率，而非再叠一层不正确的永久缓存。

实施步骤：先按技能/事件计数和计时 → 找重复纯计算 → 使用事件级或明确状态版本缓存 → 仅重算受影响项。血量、距离、手牌、技能和选择组合变化都可能使缓存失效。

Worker 仅迁移能用纯数据快照计算的工作，例如目录索引或隔离 AI 评估；当前规则函数大量依赖 `lib/game/ui/player`、函数对象与 DOM，不能直接 `postMessage` 整个引擎。需要设计序列化状态、取消、过期结果丢弃与规则版本一致性；只有 profile 证明值得时才实施。

验收：相同固定输入/可复现测试种子产生同样合法选择和事件顺序；首回合与重复回合分别测量；避免为追求速度跳过技能判断或改变联机结算。

### 6.10 PERF-10：动态媒体、观察器与长时间运行〔P2，待实测〕

涉及：`extension/红楼幻境/appearance.js`、`motion.js`、皮肤服务，以及用户实际启用的动画扩展。

红楼幻境已有 rAF 合并调度，但外观模块仍通过 subtree MutationObserver 和每秒定时任务检查；动画模块已有视频限制与回退。应测量其激活场景与频次，不把已有实现描述成完全没有生命周期管理，也不仅凭使用 MutationObserver 就认定泄漏。

实施步骤：

- 角色、皮肤和模式变化优先发明确事件；缩小观察范围；定时兜底仅在当前功能活跃时运行。
- 视频预算跨所有扩展统计，包括可见播放器、预备播放器、后台音频和 GPU纹理。试行标准档最多两个活跃视频、低档一个或静态，最终按真机负载调整。
- 后台标签页暂停非必需动画；关闭面板/更换皮肤/销毁对局清理 rAF、timer、observer、事件监听、媒体和 Blob URL。
- 提供明确质量档：完整、均衡、静态。自动降级参考持续慢帧/视频掉帧并设置恢复迟滞，防止档位反复切换；保持用户选择和核心玩法。
- 语音按实际触发加载，背景音乐按需流式播放；不将全部音频解码到 Web Audio 缓存。

验收：开关动态、切后台再返回、连开皮肤面板、死亡到结算、重进模式与连续运行 60 分钟后，媒体和节点数量稳定；静态回退可读可玩，原画不会无限重试。

### 6.11 PERF-11：失败、超时和版本一致性也是性能验收〔P1/P2，已证实〕

涉及：`noname/init/import.ts`、`noname/init/index.ts`、扩展恢复、配置事务与发布清单。

当前武将导入失败会记录错误，启动还使用 `Promise.allSettled`；需要在阶段结束后验证“必要集合已就绪”。不能只因 Promise 都结束了便认定对局可用。

建议引入阶段状态：`idle → fetching → registering → ready / failed / cancelled`。记录期望项与完成项；可选资源失败可回退，必需模式/技能缺失必须提供明确错误、重试或返回。启动 watchdog 当前按进展刷新，但同步长任务也会阻止计时器运行，所以它不能替代性能监测。

重试必须幂等，动态 import 超时并不代表模块已经停止执行；旧任务迟到时应依靠阶段 generation/version 丢弃提交。不能通过随意增加 query 重复执行同一扩展来“清缓存重试”。保留用户启用开关、存档、事务提交等待和扩展恢复语义。

联机优化要保留客户端/host 包清单、依赖注册顺序与 build 校验。服务端排队、网络往返、客户端收包到反馈分别埋点。没有 trace 证据前不做数据库、WebSocket 或托管进程架构的大改。

## 9. 开发时应避免的具体误区

1. **全局打开压缩**：旧 step 技能读取函数源码，必须保护标记和变量语义。
2. **所有扩展同时 import**：下载并行同时带来执行并行/顺序变化，可能破坏补丁与注册顺序。
3. **只提前显示大厅**：若点击模式后仍要加载同一大图，等待只是换了位置；两个阶段均要达标。
4. **一次预加载所有素材**：扩大网络竞争和解码内存；以当前场景优先。
5. **只把 DOM 隐藏当作虚拟化**：节点创建、监听器、遍历和状态检查仍在。
6. **只用微任务或 setTimeout 延迟整块工作**：计算主体仍可能长时间阻塞，必须限制每个任务实际执行时间。
7. **删除所有强制刷新或改公共图片接口为 async**：会破坏动画与立即复制背景的既有契约。
8. **对无 hash 的固定 URL 设置永久缓存**：发布后可能出现旧新代码混用。
9. **只看 Lighthouse 或平均 FPS**：它们不能覆盖选将、技能、联机和长时间内存增长。
10. **用延长超时掩盖等待**：进度、故障定位和可恢复必须与真实速度一起改善。
