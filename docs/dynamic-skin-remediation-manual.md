## 0. 执行摘要：怎样才允许宣布整改完成

### 0.1 “完美运行”的交付定义

本项目采用可检查的严格定义：**冻结的交付皮肤清单、功能清单、设备及客户端矩阵内，所有条目都有完整验收记录，全部通过；已知显示、交互、数据和稳定性缺陷为零；未验证项为零；无法解释的画面差异为零。**

不得以“可以加载”“大多数看起来正常”“几个样例通过”“没有收到新截图”宣布完成。用户不承担发现剩余问题的责任。

这项承诺以明确列出的版本、环境、素材和操作为边界。测试不能证明未知设备、未来新素材及无限操作组合永不出错；这些不能被写成已经获得的保证。对于本次约定范围内的失败，必须修复并重验，不能借此边界说明降低标准。

默认整改范围为当前目录中的全部 **4,934 条皮肤**，包括当前标记不可用的 **54 条**。文件缺失、模型损坏和没有绑定武将的情况必须分别处理：缺文件不能靠播放器生成缺失人体；需要找到正确素材并验证。未经用户明确同意，不得通过删条目、隐藏失败、取消绑定、改成静态或减少支持平台来获得“100%通过”。

### 0.2 五条不可违反的要求

1. 先确定原配置和原播放约定，再修适配；禁止继续以皮肤 ID、中文名、临时截图坐标驱动生产补丁。
2. 保留用户源素材、存档和工作区已有改动。整改过程可回退，现有正常显示有独立对照。
3. 单模型解码、图层坐标、镜头构图、时间行为、界面布局分开检查，不能相互替代。
4. 对照来源独立且可追溯。旧实现保持一致只说明“没变”，不能证明“正确”。
5. 每轮修改都提供影响清单和证据；最终执行全量验收。验收失败不得打包成“已完成”。

### 0.3 交付判定公式

```text
冻结目录数 = 已通过数 + 未通过数 + 待验证数
最终通过率 = 已通过数 / 冻结目录数

允许交付：通过率 = 100%，未通过数 = 0，待验证数 = 0，
          已知范围内缺陷 = 0，发布包检查通过，回退演练通过。
```

一条皮肤只有在所有适用验收单元通过时，才能计入“已通过”。同一皮肤的缩略图通过而大图失败，整条仍失败；缺少真实设备验证，相关设备单元仍待验证。

### 1.2 已确认的架构事实

- 千幻聆音负责皮肤选择和相关界面。本地动皮通过接入层进入另一套本地播放器；在千幻界面中出错，不足以证明是千幻原版故障。
- 本地导入保留了部分原始配置，但索引阶段会补背景、选择完整模型、归一化标记、计算图层校准。
- 运行阶段存在基于可见像素、附件名称、边界比例和人物位置的构图推断。这些会改变原始构图。
- 项目中的常规动皮接入路径按各层配置解释位置、比例和角度；本地播放器还会重新计算整幅画的镜头。两条路径尚未由完整规范证明等价。
- 本地播放器分支和骨骼版本并非一一对应。`engine42` 这个变量名也不能单独作为实际运行时版本的证据；必须记录真正的实现和资源版本。
- 本地包内有运行时代码副本。只修改源码、不更新副本，或者只更新部分包，都会造成修复不一致。

### 1.3 已有测试能够和不能够证明什么

历史记录包含 41 项单元测试、31 个前后对照样例、多个大图/缩略图回归、延迟首帧检查和实际游戏检查。这些证据继续保留，但不构成全库验收。

现有 `dynamic-case-analysis.mjs --native` 从当前播放器的 `entry.models` 读取模型，并复用 UV 修正。模型可能已经过导入替换。因此它是局部诊断工具，不能直接作为独立的“原版正确画面”。

现有 `dynamic-runtime-audit.mjs` 的骨骼计算对照复用了二进制读取器，而且只覆盖特定版本与部分计算过程。它不能独立证明二进制解析正确、贴图正确或最终构图正确。

当前 `audit-dynamic-models.mjs` 部分旧格式分支直接使用 `SkeletonBinary`；必须核对它与生产中的版本路由和 `createLegacyParser` 是否一致，再把其结果用于隔离素材。不能让测试工具误判后自动隐藏原本可用的皮肤。

历史文档可能包含旧数量、旧缓存版本、已删除的个例规则、不同服务端口。必须以本次冻结的代码与清单为准；历史文字不是最终实现的事实来源。

## 3. 整改原则与目标结构

### 3.1 应建立的确定性链路

```text
冻结源包 + 原始配置 + 原播放约定
                 ↓
资源/版本/依赖核验 → 不可用原因清单
                 ↓
按来源和格式选择经过验证的配置解释器
                 ↓
生效场景描述（每层坐标、动作、混合、遮罩、视口）
                 ↓
按精确支持能力选择渲染后端
                 ↓
统一呈现接口 → 缩略图 / 大预览 / 局内头像 / 互动
                 ↓
独立参考对照 + 全量检查 + 人工视觉审查 + 发布验收
```

“解释器”是对配置语义的解释，不等于再写一套通用骨骼解析器。能够可靠复用匹配版本的现有播放实现时优先复用；确需适配时保留差异测试。

### 3.2 职责分离

- 解码器只回答资源怎样构成骨骼、网格和动画，不决定头像应放大几倍。
- 配置解释器回答原字段的单位、默认值和覆盖关系，不靠皮肤中文名猜含义。
- 场景层决定角色、背景、前景和特效的组合，保留原始绘制顺序与坐标。
- 呈现层将已确定的场景放入指定画框；额外取景必须有单独的配置来源和验收。
- UI 层负责尺寸、按钮、文字和状态；不能通过遮挡异常、叠一张图或扩大容器掩盖渲染错误。

### 3.3 三类信息必须分别保存

1. **源事实**：原文件、原配置、资源头版本、原播放参考，不可覆盖。
2. **验证后的转换**：转换规则版本、输入输出、适用类别、误差、审核证据，可重现。
3. **待确认推断**：没有独立证据的模型选择、背景识别、人脸定位，只能用于诊断或受控实验，不得静默升为全库默认。

原配置不能被处理后的 `entry.models` 代替。没有采用某项坐标校准，也不等于原始两层已经同单位；必须保留已知不一致的证据。

## 6. G1：全库库存、分类与字段审计

### 6.1 每条记录的最低字段

为每个目录条目建立稳定记录：包、ID、标题、武将绑定、源路径、源配置哈希、实际配置、生效模型、源模型、模型哈希、图集及页贴图哈希、格式、实际版本、播放后端、图层角色、动作及持续时间、静态背景、遮罩、混合方式、透传字段、忽略字段、可用状态、失败原因、审核状态。

模型相同不等于条目相同：同一模型对应不同纹理、背景、焦点、动作、速度、皮肤或隐藏插槽时，保留单独验收身份。资源可按哈希去重读取，验收身份不能去重丢失。

### 6.2 分类必须依据结构

至少按以下维度组合，而不是只按武将或美术名称分组：

- 骨骼类型：二进制/JSON、实际 Spine 版本、Live2D 模型与运行库版本。
- 配置来源：旧动态配置、其他包的场景布局、人工明确声明的转换格式。
- 图层：单透明人物、单模型内嵌背景、人物加背景、多前后景、混合版本层、静态底图加骨骼。
- 几何：头像裁切模型、完整模型、矩形/非矩形遮罩、图集旋转与裁切、多页图集。
- 动画：出场后待机、循环待机、背景专用动作、变身、多轨、事件动作、随机分支。
- 取景：源头像画框、源场景画框、明确指定焦点、未声明视口。
- 资源状态：完整、缺失、错误引用、版本未知、解析异常、暂无法建立参考。

分类结果必须可程序重建；新增皮肤应自动进入相应类别或明确的未知队列，不依赖人工记住某个皮肤的特殊性。

### 6.3 字段覆盖表

从原配置自动统计字段、值类型、出现次数、默认值和当前消费者。至少覆盖：

`name / action / animation / x / y / scale / angle / speed / width / height / flip / skin / hideSlots / clip / opacity / background / beijing / shizhounian / entrance / attack / transform / interactive / voice`。

该清单是审计起点，实际出现的其他字段必须登记。名称相近不等于语义相同；`undefined`、`null`、`0`、空数组、缺字段分别核对。特别检查 `value || default` 把合法零值替换掉的情况。

每个实际字段必须归入：精确支持、已验证转换、明确不适用、尚不支持。未知字段不能悄悄丢弃。全库支持率与字段解释覆盖率分别报告。

### 6.4 54 条不可用条目的处理

对每项重新核验：源文件是否存在、大小和哈希是否正常、图集引用是否匹配、解析器是否选错、模型与图集是否属于同一导出版本。

解析器误判归代码缺陷；引用可确定修复归导入缺陷；源包确实缺文件归素材缺陷。后者必须补齐正确资源才能通过。无来源的部件不得通过复制其他皮肤或拉伸邻近纹理伪造。

隔离是避免运行崩溃的措施，不等于整改完成，也不减少验收分母。

## 7. G2：建立真正独立的正确性参考

### 7.1 参考来源顺序

1. 与源素材及配置配套、能够确定版本和使用方式的原播放程序。
2. 相匹配的运行时与原配置解释器，使用明确的参考视口和真实源文件。
3. 来源可信的原始演示或作者确认画面，用于核对构图；不能单独证明内部解析正确。
4. 若前述均缺失，只能建立“待核验”的参考候选；不得把当前错误画面挑一帧当正确基线。

不能默认“原版一定正确”。若原配套路径也出错，需要区分源配置问题、缺资源、运行环境问题与本地适配问题，并把责任记录到具体环节。

### 7.2 参考播放的必备记录

保存原模型路径/哈希、原图集和页纹理、原配置、原作者/来源版本信息（若有）、渲染库哈希、配置覆盖层、视口、参考画框尺寸、DPR、动作名称、时间、随机种子、颜色与透明度约定。

源画框尺寸和 `180` 一类基准值必须有来源。当前接入代码使用了高度基准，不代表每个包、每种预览天然都遵守它。固定偏移量与百分比位置随容器放大时如何变化，必须由原逻辑确认。

### 7.3 独立性检查

| 对照环节 | 不合格做法 | 合格要求 |
| --- | --- | --- |
| 模型选择 | 原版对照读取已替换的 `entry.models` | 从冻结原配置直接解析源引用 |
| 解析 | 两边用同一未验证读取器，再宣布解析正确 | 精确版本的独立读取实现或可验证导出对照；若共用需明确剩余盲区 |
| UV/透明度 | 对照侧也自动套当前修复 | 保留原路径和独立参考路径，记录每个必要调整 |
| 配置 | 两边都读处理后的坐标 | 原配置、覆盖配置、生效配置分别记录 |
| 时间 | 两边启动后随便截图 | 同动作、同逻辑时间、同随机种子和更新步长 |
| 画框 | 两边视口和比例不同 | 一致的比较视口；额外呈现策略单独验收 |

### 7.4 根因定位实验

按变量分组比较，不能同时更换模型、比例和播放器后仅凭画面改善推断原因：

1. 同源资源、同解码器，比较原配置摆放与当前生效摆放。
2. 同源资源、同摆放，比较独立解码/渲染实现。
3. 同模型和时间，只切换导入模型选择。
4. 同场景，只切换呈现视口及 UI 容器。
5. 同配置，逐层显示背景、主体、前景、特效、遮罩，再合成。

每个实验记录唯一改变的变量、假设、观察、结论与未排除因素。不能把“改后看起来好”当成唯一根因证据。

## 8. G3：配置与坐标契约

### 8.1 每种来源必须明确的契约

| 项目 | 必须回答的问题 |
| --- | --- |
| 位置 | 数字是骨骼单位还是逻辑像素？数组是否为固定偏移加容器比例？比例参照哪一层容器？ |
| 坐标轴 | 原点在哪？Y 向上还是向下？根骨骼负缩放怎样解释？ |
| 比例 | 原比例、参考画框缩放、用户缩放分别在哪一步应用？是否有宽高适配覆盖比例？ |
| 旋转 | 角度单位、方向、旋转中心、与缩放/平移的执行顺序是什么？ |
| 图层 | 前后景与主体是否同单位、同参考框、同时间？哪些层本来独立摆放？ |
| 画框 | 头像框、大预览和场景预览各自的源意图是什么？ |
| 遮罩 | 应用于骨骼插槽还是整体输出？结束插槽、换序及变身怎样处理？ |
| 动作 | 配置动作不存在时怎么办？出场接哪个待机？背景与人物是否同步？ |
| 覆盖 | 源配置、主题编辑、用户编辑、明确修复配置的优先级是什么？ |
| 默认值 | 缺字段与零值的含义；是否允许镜像、暂停、透明度零？ |

### 8.2 统一坐标模型

可用下列模型表达职责，但具体矩阵顺序必须按每个来源的原逻辑核实：

```text
屏幕坐标 = 设备像素变换 × 呈现变换 × 场景图层变换 × 骨骼动画后的顶点
```

骨骼动画和约束计算完成后再施加外部图层变换。不要为了构图直接改根骨骼数据；不要在图层和相机两处重复乘源配置缩放；DPR 只在约定位置进入设备像素转换。

必须测试旋转后的平移、负比例、非中心原点、固定偏移加百分比位置、不同宽高比、相同逻辑尺寸不同 DPR。把最终矩阵或等效参数写入诊断记录，便于解释每次显示。

### 8.3 模型选择与图层校准

- 默认忠实加载原声明模型。头像与完整模型是不同用途，不能因文件名存在 `daiji` 就替换 `daiji2`。
- 需要完整预览时，优先采用源包明确声明的完整模型或预览设置。
- 几何/UV匹配可作为辅助证据，但不能单独证明替换模型、改变姿态或重新取景合理。
- 几何对齐只有在角色部件、拓扑、动画时序、纹理比例和构图用途都成立时才可应用。
- 不采用转换时仍保留“已证实坐标不同”“对应模型尚未证实”等事实，禁止下游再次猜成同坐标。
- 每个转换都要记录生效前后数据和原因；同一变换不得重复应用。

### 8.4 取景不能同时承诺互相冲突的结果

当源画面与头像框宽高比不同，“完全显示整幅画”“铺满画框”“不变形”“不裁切”通常不能四者同时成立。不能为达成表面铺满而拉伸人体或随意放大。

按明确用途处理：

- 源头像：恢复原头像构图，允许原作者设计的合理裁切。
- 完整场景预览：保持比例展示声明的完整场景，画框策略明确。
- 透明单人物：根据声明或已验证的人物范围呈现，允许真实透明区域。
- 未声明用途：先确立参考与展示策略；不自动把某张皮肤的参数推广给全类。

验收关注“相对正确参考出现的非预期裁切、空带、变形和层错位”。不能把所有透明像素判错，也不能把源头像本来不显示双脚认定为缺腿。反过来，遮罩错误造成的身体切断必须修复，不能解释成艺术设计。

## 9. 渲染正确性专项清单

### 9.1 版本与解析

- 读取实际资源版本；版本路由使用明确能力表，不能用粗略数字大小覆盖所有旧格式。
- 二进制方言、JSON结构、默认皮肤/非默认皮肤、linked mesh、变形动画、绘制顺序、IK及其他约束逐项测试。
- 图集与骨骼必须配套。未知字段、非法数据和解析不完整必须带条目与资源路径报告。
- 混合版本图层分别选择正确后端；离屏转成纹理时保留坐标、比例、透明度、时间和分辨率。
- Live2D单独建立模型、纹理、动作、表情、物理、口型、命中区的能力清单；不套用Spine构图结论。

### 9.2 纹理、UV与透明度

- 对图集旋转、原尺寸、裁切偏移、多页、透明边和不同页尺寸建立数值夹具。
- 验证普通、加色、滤色及源素材使用的其他混合方式，区分纹理是否预乘。
- 覆盖图片解码、ImageBitmap、纹理重传和WebGL上下文恢复；上传状态不能污染其他纹理。
- 在黑、白、中灰三种诊断底色检查白边、黑边、矩形块和半透明接缝。诊断底色不得混入正式缩略图。
- 保持正确网格UV，禁止通过伸展贴图遮盖骨骼解析或缺附件问题。

### 9.3 遮罩与层级

- 保留原插槽顺序及动画中的换序；检查矩形和非矩形clipping的起止范围。
- 检查隐藏附件、皮肤切换、透明度零、特效层、背景层和独立静态底图。
- 身体缺失时同时核查源附件、皮肤选择、遮罩、绘制顺序、UV和动作，不先认定模型坏或比例错。

### 9.4 动画和时间

- 出场只播放规定次数，结束进入指定待机；不同来源的同名动作不能自动认为含义相同。
- 背景、人物和特效使用明确时间基准；不能在多个ticker中重复推进。
- 禁止用每帧可见边界不断重算固定头像相机，引入非源动画的“呼吸式缩放”。源动画本身的镜头运动应保留。
- 覆盖暂停/恢复、页面隐藏、首个负时间增量、循环边界、打断、互动返回、变身及不同播放速度。

## 10. 现有推断规则的迁移要求

整改不能把所有旧规则一次删除，也不能把它们原封不动隐藏在新接口后面。为每项建立“规则登记表”：输入、输出、适用范围、来源证据、受影响ID集合、正确参考、去留决定、测试与回退方法。

| 现有规则族 | 需要回答的问题 | 迁移目标 |
| --- | --- | --- |
| `avatarLayerTransform` 的高度/比例推断 | 是否替代了源配置？是否重复缩放？ | 用明确的配置语义或已验证转换取代猜测 |
| `sceneFocus` 的参考高度与横向焦点 | 基准尺寸有何来源？Y/旋转/主题编辑是否被遗漏？ | 按来源的完整视口契约解释 |
| `sceneBounds / recoverSceneBounds / trimPortraitEdges` | 是否把不透明衣服、小背景块或云雾当画框？ | 诊断与呈现分离；明确画框优先 |
| `subjectBounds` 附件名称识别人脸 | 是否误认马、动物、躯干或另一人物？ | 仅辅助检测；不作为所有素材的默认摄像机 |
| `sceneVariant` 完整模型选择 | 是否改变用途、层级或动作？ | 源声明优先，有独立证据才转换 |
| `layerRegistration` | 几何匹配是否只来自同一特效或背景中另一角色？ | 验证语义、动作及用途，完整记录证据 |
| `layerCoordinateMismatch` | 拒绝校准后是否仍保留已知差异？ | 保留诊断事实，禁止后续归零变换 |
| `idleAnimation` 名称替换 | 是否把作者指定的特殊动作改掉？ | 来源动作状态机优先，未知报待确认 |
| 静态背景延展与填充 | 是否掩盖原图裁切或叠加其他人物？ | 源画框策略，禁止用遮盖代替修复 |

保留或删除任意一项都必须有前后证据。已有历史个例预设同样需要登记，不能因为“早就存在”跳过审计。

## 11. 加载、首帧、交互和界面统一

### 11.1 加载状态机

建议实施明确状态：`created → loading → decoded → composed → firstFrameReady → visible → disposed`，并包含 `error / cancelled` 分支。此状态机是整改要求，不代表当前已完整实现。

- 只有最终尺寸、最终配置和正确初始动作完成一次绘制，才允许公开可见画布并发送ready。
- 采样画布、临时容纳画面和未完成背景不能被用户看到或写入缩略图缓存。
- 每次挂载分配generation标识。快速切换A→B→C时，A/B的迟到加载、消息和截图不能覆盖C。
- 取消加载后必须释放资源；销毁后不能继续绘制、出声或接受旧消息。
- 通信校验来源、频道、条目ID和generation，避免另一iframe的就绪/错误影响当前预览。

### 11.2 统一呈现，明确不同视口

缩略图、大预览、局内头像和互动使用同一条已验证的配置解释链路。允许视口不同，但策略必须显式；不能每处单独再猜一次人物比例。

缩略图记录捕获时间和呈现策略。与大预览比较时使用同一动作时间，不能把不同动画帧的正常差异误报为错误。

### 11.3 UI专项

- 交互按钮按真实绘画容器定位，不能依赖隐藏控件或错误父节点；静态状态下遵循现有产品行为。
- 标题、来源和详情文字必须留在规定边界内；长标题、混合中英文、特殊字符、换行和系统缩放都需验证。
- 显示名称与内部ID分离；修文字不能破坏选中、保存、排序和静动切换。
- 主将/副将、隐将揭示、死亡、换肤、页面关闭、横竖窗口变化均有生命周期用例。
- 交互动作结束后恢复正确待机与视口；暂停、静音、音量及口型状态不丢失。

### 11.4 缓存契约

缓存键至少包括：皮肤身份、源资源修订、解释器版本、模型选择、配置修订、运行时修订、呈现模式、尺寸/DPR策略和截图时刻策略。

`ready`只证明某帧已就绪，不自动证明视觉通过。缓存不得写入加载中间帧或失败占位图。算法更新后相关缓存必须自动失效，不能要求用户逐个清理。

测试冷缓存、热缓存、旧版本迁移、缓存损坏、空间不足、快速取消和离线重开。回退时选择对应旧命名空间或安全失效，不混用新旧结果。

## 12. G5：全量验证矩阵

### 12.1 核心矩阵

| 维度 | 必须覆盖 |
| --- | --- |
| 条目 | 冻结清单全部4,934项；新增条目另立批次，不偷换分母 |
| 入口 | 列表缩略图、大预览、所有适用的局内头像及已声明互动 |
| 尺寸 | 现有360×600、240×360回归；另从实际UI收集最小/默认/最大画框；测真实窗口1440×900和1100×720 |
| 像素密度 | DPR 1、1.25、1.5、2及实际部署中使用的组合 |
| 生命周期 | 首次打开、冷/热缓存、切换、重开、暂停/恢复、隐藏/显示、销毁 |
| 动画 | 入场、待机、每个声明动作、返回待机、变身及循环边界 |
| 时间 | 最终首帧；按动作持续时间采样；循环前后；长时间播放 |
| 渲染 | 实际资源版本、图集/遮罩/混合方式和所有生产后端 |
| 场景 | 人物与背景合成、单层诊断、源头像与完整场景的适用模式 |
| 数据 | 绑定、已保存选择、静动切换、名称、音量、禁用配置 |

“不适用”必须有结构依据，例如无语音的条目可不测语音播放，但不能因为动作当前报错就标成无互动。未绑定条目可在诊断容器验收，禁止为方便测试自动绑定到同名武将。

### 12.2 时间采样

每个声明动作记录持续时间D。最低采样包含初始正确帧、D/4、D/2、3D/4、D−ε、D+ε；循环动作还包含2D附近。ε依据测试帧间隔确定，不使用固定0.5秒覆盖全部素材。

入场与返回待机的两个转换边界必须连续录制。每项的待机至少检查两个完整周期；特别长或无有限周期动作采用固定窗口并记录限制，不能伪称已覆盖整周期。

长时间验证至少包括各类别代表的10分钟稳定播放和实际游戏30分钟操作场景。仅有多个静帧不能证明过程中没有闪烁；全条目的适用入场/循环段应生成可复查录屏或连续帧证据。

### 12.3 全量与抽样的分工

- 全量自动：依赖、版本、字段解释、解析、加载、矩阵记录、画面捕获、声明动作运行、已定义异常检测、缓存和结果落盘。
- 全量视觉：每条至少有可读的参考/候选画面及动作概览，并有审查状态。可用分组联系表和短视频提高效率，不能以“自动没报警”代替视觉通过。
- 代表性深入测试：组合爆炸的竞态、压力、上下文恢复和特殊交互，按结构类别设计；被修改规则涉及的全部条目必须重验。
- 自动指标存在盲区时，增加专项审核或完善检测，不把检查工作转交给用户。

对图像/视频审查必须使用实际查看图像的能力；只读取文件存在、像素总数或模型边界，不构成视觉审核。

### 12.4 自动异常检测要求

至少报告：加载失败、缺资源、非有限矩阵/顶点、空画布、非预期透明带、主体超框、图层错位、循环边界突变、相机非预期漂移、缩略图和预览不一致、文字/按钮越界、过期结果覆盖、资源泄漏。

这些是“疑似异常”检测，不是审美真值。透明人物不能套用背景不透明率标准；马、龙、宠物和粒子不能充当主体；不能仅按附件名判断头部。

## 13. 数值、视觉与性能验收标准

### 13.1 功能硬门槛

| 检查 | 交付门槛 |
| --- | --- |
| 清单闭合 | 冻结目录每项都有结果；重复、漏项、隐式跳过均为0 |
| 资源与解析 | 范围内必需资源缺失0、错误版本路由0、未解释解析错误0 |
| 人物显示 | 相对正确参考的非预期主体裁切、缺部件、错误缩放和变形0 |
| 背景与层级 | 非预期空带、矩形接缝、图层分离、遮罩缺失0 |
| 时间 | 非源动画的反复缩放、错误循环、首次闪图、切换串图0 |
| UI | 标题/来源越界0、按钮定位错误0、选择与显示不一致0 |
| 存档 | 原选择与绑定丢失0、跨武将误绑定0、正式存档被测试污染0 |
| 错误日志 | 受测操作产生的未处理异常、非预期资源失败、持续WebGL错误0 |

“0缺陷”指所有检测和审查记录中已知缺陷归零，不伪称形式化证明任何未来操作都不出错。

### 13.2 数值与画面对照

以下为建立测试的默认精度目标；在G2用同一正确实现重复渲染测量噪声后锁定。不能因候选失败直接提高容差。

- 源文件和不可变配置：哈希完全一致；允许转换的字段逐项有记录。
- 同设备、同运行库、同输入的静态初始帧：优先要求确定性一致；已知随机性必须固定或分离。
- 坐标对照：统一到逻辑像素后，静态定位偏差默认≤0.5px；跨后端栅格误差必须测量并记录，不用原始骨骼单位随意设阈值。
- 图像比较：记录像素差、边界、透明区、关键部件及感知差异；相似度高不能覆盖“脸被裁掉”这样的局部失败。
- 动态特效：允许经证实的非确定性区域单独比较统计性质，但遮罩不能覆盖主体或整个画面来消除报警。
- 缩略图对照：同时间、同呈现策略，允许尺寸采样差异，禁止漏层和构图策略不一致。

### 13.3 性能与资源

G0必须选定用户实际使用的目标机器，记录显示器刷新率和实际生产并发限制。软件渲染浏览器可做功能回归，不能代替真实GPU性能验收。

默认验收目标：

- 沿用现有帧率、分辨率和并发能力，不通过降清晰度或停动画获得“通过”。60Hz桌面以持续60fps为目标，稳定播放阶段建议帧耗时P95≤20ms、P99≤33.4ms；需要以固定场景、实际硬件和完整性能报告锁定。
- 与可信旧实现同场景比较，稳定帧耗时P95不退化超过10%；若旧实现已经不合格，还必须达到绝对目标，不能仅维持旧的卡顿。
- 冷启动在未进入动皮场景时保持按需加载，不全量加载模型与纹理；统计模型请求与目录请求时分开记录。
- 素材加载时间按资源大小和冷热缓存分别记录P50/P95。G0必须填入目标机器的上限；未填上限不能在最终报告称为性能通过。
- 连续打开/关闭及换肤至少200次后，活动播放器、观察器、事件、ticker、音频和纹理计数回到预期；不得持续单调增长。
- 在同一引擎垃圾回收可观测条件下，200次操作后的稳定保留内存建议不高于预热平台的110%；浏览器自身波动必须与资源计数和堆记录一起解释。
- 关闭或后台暂停符合原功能约定；恢复后无加速追帧、漏层和错误动作。

性能目标必须在实施前锁定。确需改变产品能力或目标环境时，由用户明确决定；执行者不能为了交付自行放宽。

### 16.1 缺陷记录模板

每项必须填写：

```text

来源：用户反馈、全库扫描、视觉审查、回归、实际设备

初步分类：资源 / 解析 / 纹理 / 配置 / 合成 / 取景 / 时序 / UI / 缓存 / 生命周期
根因证据与排除项
```

把同根因条目挂在同一缺陷族下，但保留各自验收记录。不要给每个皮肤复制一套位置补丁；也不要在根因未确认时把所有相似截图直接合成一个问题。

### 16.2 严重度

- 阻断：崩溃、数据丢失、无法加载、错误归属、持续资源泄漏、错误实现被大范围发布。
- 严重：人物缺失/被非预期截断、层错位、比例明显错误、闪图、循环镜头异常、主要功能不可用。
- 一般：文字/按钮越界、缓存陈旧、局部视觉差异、非关键操作异常。
- 轻微：可见但不影响功能的细节差异。

严格交付要求范围内已知缺陷全部关闭，轻微级别也不能被自动忽略。确属参考差异而非缺陷时，必须有依据和审查记录。

### 16.3 每轮修改的必需附件

变更目的、配置契约变化、规则ID、影响条目全集、原始对照、修复后证据、非目标类别回归、缓存/安装迁移、性能变化、回退操作。

禁止修改测试期望来迁就错误画面；正确参考的变化需要独立审查和理由。测试夹具允许使用皮肤ID，生产逻辑应依据来源格式、显式元数据或已验证结构。

## 17. 发布、升级与回退

### 17.1 候选包发布检查

每次发布生成一份清单，包含源码版本及工作区快照标识、导入工具版本、场景协议版本、运行库哈希、各包目录修订、条目数、源资源哈希、缓存策略和已验收报告ID。

确认四个包的运行时副本与预期源码一致；检查所有实际运行文件与供应库，不仅检查历史的20个文件。确认安装后的真实资源路径，不以源码目录测试替代安装物测试。

发布应使用暂存候选目录和明确的切换步骤，防止用户在索引更新到一半时读到新旧混合数据。先完整写入资源/条目，最后发布可见索引；还要处理播放器副本与缓存版本的一致切换。

### 17.2 必须覆盖的安装场景

1. 干净测试存档首次安装与首次选择。
2. 当前用户版本升级，保留选择、绑定、音量和开关。
3. 已有旧缩略图缓存升级，自动得到正确新画面。
4. 导入中断或候选验证失败，正式安装仍可用。
5. 同名包更新、文件增加/删除、被修复的不可用条目恢复。
6. 回退到基线，元数据、运行时和缓存不会混用。

### 17.3 平台范围

当前已知主要验证环境是Windows浏览器和本地开发服务，不能据此宣称EXE、APK、Android真机均通过。

G0必须登记用户实际交付渠道。属于本次既有支持承诺的EXE/APK或其他渠道必须纳入实机安装验收；不是本次交付渠道的可以记录为不适用，但不得在宣传或结论里冒称已验证。未确定渠道标为待确定，不静默当成已通过。

### 17.4 回退触发

出现新的人物裁切、原正常类别变化、崩溃、存档错误、长时间卡顿、未知大范围差异，停止候选发布并回退相应类别或整份候选。回退保留诊断数据，不清除失败记录。不得以“再清一次缓存试试”代替根因调查。

## 20. 给整改人员和后续代理的执行指令

以本手册为整改与验收规范。首先保存现场和原始素材证据，核对当前代码与本文快照的差异，再建立全库库存及独立参考。优先处理配置语义和版本路由，不沿用“用户给一张截图就补一条取景规则”的方式。

实施中主动发现同类条目并检查全部影响范围；图像审查由执行者完成。只能在确实缺少原始资源、交付范围信息或不可替代的用户决定时向用户提出具体问题，不能把全库排查交回用户。

保留原界面和已有功能。来源匹配的播放实现可复用，未知差异必须记录。不要为了迅速得到漂亮样例同时改变模型、动作、缩放和背景，再宣布找到了根因。

每阶段报告应先列事实：冻结总数、完成类别、通过数量、未测数量、开放缺陷、阻塞事项和证据路径。不要重复罗列工具调用，也不要把计划写成已经完成的工作。

最终只有在第19节全部有证据通过时，才交付“本次约定范围全部验收通过”。如果仍有一项失败，继续整改并保留真实状态。

## 22. 后续维护：防止重新陷入逐皮肤修补

### 22.1 新增素材准入

每次新增或更新包，先计算新增/变化的资源与配置哈希，再进行版本、字段、依赖和参考分类。已有类别也必须验证实际新条目的画面；未知类别进入待确认队列，不继承最相似武将的坐标。

新增条目在未验证前标为待验证，保留原文件和失败原因，不能静默显示错误画面并等待用户报错。是否暂时不展示待验证项属于产品发布策略，不得借此从本次冻结的4934条范围中移除问题。

### 22.2 代码变化后的重验范围

| 修改类型 | 最低重验范围 |
| --- | --- |
| 单条明确配置或资源更新 | 该条全部呈现及动作单元，加共享同资源/配置的条目 |
| 某来源配置解释器 | 使用该解释器的全部条目，加其他解释器代表对照 |
| 共用坐标、相机、UV、混合或渲染后端 | 使用该能力的全部条目；发布前执行全库汇总门禁 |
| UI布局、挂载、缓存和生命周期 | 所有入口及结构类别，边界尺寸、切换、存档和缓存回归 |
| 供应库、浏览器/客户端升级 | 相关格式完整回归及实际目标设备复核 |

### 22.3 基线维护

正确参考与旧实现回归基线分开版本管理。更新正确参考必须说明源素材、源配置或产品意图为何改变，不得因为当前实现不同就更新期望图。

每次发布保存可恢复版本和证据索引。巨大图像/视频可以按内容哈希存储和去重，但审查记录及对每条条目的映射不能丢失。新增用户反馈应触发重新打开相关缺陷和整类影响分析；用户反馈是额外信息，不是主要测试来源。

本节规定维护流程，不表示已经创建定时任务、监控或自动发布。
